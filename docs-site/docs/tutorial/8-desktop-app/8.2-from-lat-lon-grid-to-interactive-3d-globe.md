# 8.2 From a Latitude–Longitude Grid to an Interactive 3D Globe { #_1 }

The Globe view of the PlaSiC App looks like a draggable 3D Earth, but it does not use a
full 3D graphics engine. On the CPU, `ClimateGlobeWidget` computes the latitude and
longitude that correspond to each screen pixel, samples the climate field from a `Frame`,
and then hands the result to Qt for drawing.

This note explains the mathematics behind this rendering chain.

!!! tip "The most important observation"

    The climate field is rendered by **inverse mapping**: instead of pushing each grid
    point of latitude and longitude onto the screen, the code starts from each screen
    pixel, works back to its position on the sphere, and reads the field value there.

<div class="arch-flow" aria-label="Inverse mapping pipeline from screen pixels to the final color in the Globe view">
  <span class="arch-node">screen pixel</span><span class="arch-arrow">→</span>
  <span class="arch-node">sphere point in view frame</span><span class="arch-arrow">→</span>
  <span class="arch-node">sphere point in world frame</span><span class="arch-arrow">→</span>
  <span class="arch-node">longitude and latitude</span><span class="arch-arrow">→</span>
  <span class="arch-node">bilinear sampling</span><span class="arch-arrow">→</span>
  <span class="arch-node arch-node--result">RGBA pixel</span>
</div>

## 1. Coordinates, Symbols, and Conventions

To avoid getting lost among the different coordinate systems, we first fix the symbols
used in this note.

| Symbol | Meaning | Range or unit |
|---|---|---|
| $i,j$ | column and row index of the image | integer pixel index |
| $D$ | diameter of the rendered globe image | pixels |
| $(x_v,y_v,z_v)$ | unit-sphere point in the viewer frame | dimensionless |
| $(x_w,y_w,z_w)$ | unit-sphere point in the Earth-fixed (world) frame | dimensionless |
| $\lambda$ | longitude, positive eastward | radians |
| $\phi$ | latitude, positive northward | radians |
| $\psi$ | yaw, horizontal rotation angle | radians |
| $\theta$ | pitch, vertical tilt angle | radians |
| $s$ | zoom, scale of the sphere relative to the drawing area | dimensionless |
| $n_{\mathrm{lon}},n_{\mathrm{lat}}$ | number of longitude and latitude grid points in the field data | positive integers |

The App uses a right-handed convention:

- the $x$ axis points to the right of the screen;
- the $y$ axis points to the North Pole;
- the $z$ axis points to the viewer in the viewer frame, and to the $0^\circ$ meridian in
  the world frame.

![Coordinate frames and interaction angles of the Globe view](<../assets/images/globe-axes-and-yaw-pitch.png>)

*Figure 8.2.1. Coordinate setting.*

The sphere radius is normalized to 1, so every point on the sphere satisfies

$$
x^2+y^2+z^2=1.
$$

### 1.1 Two Coordinate Sets for the Same Point

The subscript $v$ stands for "view", i.e. the viewer frame; the subscript $w$ stands for
"world", i.e. the Earth-fixed frame. After the user rotates the globe, the same sphere
point has two different coordinate triples:

$$
\mathbf v=
\begin{bmatrix}x_v\\y_v\\z_v\end{bmatrix},
\qquad
\mathbf w=
\begin{bmatrix}x_w\\y_w\\z_w\end{bmatrix}.
$$

The view coordinates answer "where does this point appear on the screen"; the world
coordinates answer "what latitude and longitude does this point have on the Earth". The
core of the rendering process is the conversion between the two.

## 2. Why Orthographic Projection

Orthographic projection (for the standard map-projection definition, see Snyder, 1987)
can be understood as viewing the Earth from infinitely far away, so that all projection
lines are parallel. If the line of sight is along the $z$ axis, a 3D point projects to

$$
P(x_v,y_v,z_v)=(x_v,y_v).
$$

It simply discards the depth $z_v$ and produces no "near large, far small" perspective.
Therefore the outline of the globe is always a circle. This is visually close to a distant
satellite image and is well suited to displaying global climate fields.

!!! note "Why does it look 3D?"

    What is actually shown on the screen is still a 2D `QImage`. The sphere's coastlines, the graticule, and the shading near the limb together provide depth
    cues that give the 2D orthographic projection a 3D appearance.

## 3. Recovering the Visible Sphere from Screen Pixels

### 3.1 Normalizing Pixel Centers

For a square image of diameter $D$, the center of pixel $i$ maps to

$$
u_i=2\frac{i+\tfrac12}{D}-1,
\qquad i=0,1,\ldots,D-1.
$$

The term $\tfrac12$ selects the pixel center rather than the pixel edge. Hence the
horizontal coordinates are evenly spaced inside $(-1,1)$. The vertical direction uses the
same mapping, but Qt image coordinates increase downward while mathematical coordinates
increase upward, so we must flip the sign:

$$
x_v=u_i,
\qquad
y_v=-u_j.
$$

This corresponds to the code

```python
coordinate = (np.arange(diameter) + 0.5) / diameter * 2.0 - 1.0
view_x, screen_y = np.meshgrid(coordinate, coordinate)
view_y = -screen_y
```

### 3.2 The Unit Circle Is the Globe Outline

A screen point lies inside the globe disk exactly when

$$
r^2=x_v^2+y_v^2\leq1.
$$

Pixels outside the circle get alpha 0, so the background stays transparent. The edge
(limb) of the sphere is

$$
x_v^2+y_v^2=1.
$$

### 3.3 Inverse Orthographic Projection

For a pixel inside the disk, the unit-sphere equation gives

$$
z_v^2=1-x_v^2-y_v^2.
$$

Only the front hemisphere, the one facing the viewer, is displayed, so we take the
non-negative root:

$$
\boxed{
z_v=\sqrt{1-x_v^2-y_v^2}
}.
$$

Thus a 2D pixel is lifted back to a 3D unit vector in the viewer frame:

$$
\boxed{
(x_v,y_v)
\longmapsto
\left(x_v,y_v,\sqrt{1-x_v^2-y_v^2}\right)
}.
$$


## 4. Rotation Is a Change of Coordinates, Not a Move of Pixels

The Globe view expresses its orientation with two angles:

- yaw $\psi$: the Earth rotates left and right about the $y$ axis;
- pitch $\theta$: the Earth tilts up and down about the $x$ axis.

The interface stores these angles in degrees and converts them to radians before calling
the trigonometric functions.

### 4.1 Why Rendering Applies the Inverse Rotation

The forward process, from world coordinates to screen coordinates, can be written as

$$
\mathbf v=R_x(\theta)R_y(\psi)\mathbf w.
$$

However, inverse mapping already produced $\mathbf v$ from the screen, and the goal is to
recover $\mathbf w$. Therefore we must use

$$
\mathbf w
=R_y(-\psi)R_x(-\theta)\mathbf v.
$$

Rotation matrices are orthogonal, so

$$
R^{-1}=R^{\mathsf T}=R(-\alpha).
$$

Note that the inverse not only negates the angles but also reverses the order of the
factors, because

$$
(AB)^{-1}=B^{-1}A^{-1},
\qquad
R_xR_y\ne R_yR_x.
$$

### 4.2 Undoing Pitch First

Before we use the 3D formulas, let us build a 2D intuition. A point in the plane can be
written as

$$
\begin{bmatrix}x\\y\end{bmatrix}
=x\begin{bmatrix}1\\0\end{bmatrix}
+y\begin{bmatrix}0\\1\end{bmatrix}.
$$

That is, every point is a linear combination of the two unit axis vectors. If we rotate
the whole plane counterclockwise by $\alpha$, the two original unit vectors land on

$$
\begin{bmatrix}\cos\alpha\\\sin\alpha\end{bmatrix},
\qquad
\begin{bmatrix}-\sin\alpha\\\cos\alpha\end{bmatrix}.
$$

The "recipe" $x$ and $y$ of the point does not change under an overall rotation, so the
rotated coordinates are the same linear combination of the two new vectors:

$$
\begin{bmatrix}x'\\y'\end{bmatrix}
=
\begin{bmatrix}
\cos\alpha&-\sin\alpha\\
\sin\alpha&\cos\alpha
\end{bmatrix}
\begin{bmatrix}x\\y\end{bmatrix}.
$$

This is why we may multiply by a rotation matrix: each column of the matrix records where
one old unit axis goes after the rotation, and the matrix product recombines the point's
components along those axes. It is not an extra computational trick; it compresses the
statement "all points turn by the same rule" into a single notation.

The 3D pitch follows exactly the same idea. When rotating about the $x$ axis, the $x$
axis itself is unchanged; only the $yz$ plane rotates like the 2D plane above. Hence the
forward pitch is

$$
R_x(\theta)=
\begin{bmatrix}
1&0&0\\
0&\cos\theta&-\sin\theta\\
0&\sin\theta&\cos\theta
\end{bmatrix}.
$$

At render time we already have the view coordinates $\mathbf v$, and the goal is to undo
this step, so as to obtain the intermediate coordinates $\mathbf p$ after yaw was applied
but before yaw was undone. Therefore we use the opposite angle $-\theta$:

$$
R_x(-\theta)=
\begin{bmatrix}
1&0&0\\
0&\cos\theta&\sin\theta\\
0&-\sin\theta&\cos\theta
\end{bmatrix}.
$$

![Why the x-rotation matrix has this shape](<../assets/images/rotation-matrix-about-x.png>)

*Figure 8.2.2. Why the $x$-rotation matrix has this shape.*

Multiplying the matrix by the column vector and evaluating the result row by row gives

$$
\begin{bmatrix}x_p\\y_p\\z_p\end{bmatrix}
=R_x(-\theta)
\begin{bmatrix}x_v\\y_v\\z_v\end{bmatrix}.
$$

$$
\boxed{
\begin{aligned}
x_p &= x_v,\\
y_p &= \cos\theta\,y_v+\sin\theta\,z_v,\\
z_p &= -\sin\theta\,y_v+\cos\theta\,z_v.
\end{aligned}
}
$$

The first line is $x_p=1\cdot x_v+0\cdot y_v+0\cdot z_v$, so rotation about the $x$ axis
does not change $x$. The other two lines mix only $y$ and $z$, which is exactly what
"rotate in the $yz$ plane" means. When $\theta=0$, we have $\cos\theta=1$ and
$\sin\theta=0$, and the three coordinates are returned unchanged; when $\theta=90^\circ$,
we get $y_p=z_v$ and $z_p=-y_v$. These two boundary checks also help to detect a sign or
direction mistake.

A rotation neither squashes nor stretches the unit sphere. The reason is that
$\cos^2\theta+\sin^2\theta=1$, so the columns of the matrix remain mutually perpendicular
and of length 1. In linear-algebra terms, a rotation matrix is orthogonal, so its
transpose both swaps rows and columns and gives the inverse:

$$
R_x(\theta)^{\mathsf T}=R_x(-\theta)=R_x(\theta)^{-1}.
$$

This also explains why "negating the angle" undoes a pure rotation without solving any
equations again.

### 4.3 Undoing Yaw

Next we undo yaw. Yaw rotates about the vertical $y$ axis, so the $y$
component is unchanged and only $x$ and $z$ are mixed in the horizontal $xz$ plane. The
forward yaw is

$$
R_y(\psi)=
\begin{bmatrix}
\cos\psi&0&-\sin\psi\\
0&1&0\\
\sin\psi&0&\cos\psi
\end{bmatrix}.
$$

As with pitch, the inverse negates the angle:

$$
R_y(-\psi)=
\begin{bmatrix}
\cos\psi&0&\sin\psi\\
0&1&0\\
-\sin\psi&0&\cos\psi
\end{bmatrix}.
$$

Multiplying it by the intermediate coordinates from the previous subsection,

$$
\begin{bmatrix}x_w\\y_w\\z_w\end{bmatrix}
=R_y(-\psi)
\begin{bmatrix}x_p\\y_p\\z_p\end{bmatrix},
$$

gives the world coordinates:

$$
\boxed{
\begin{aligned}
x_w &= \cos\psi\,x_p+\sin\psi\,z_p,\\
y_w &= y_p,\\
z_w &= -\sin\psi\,x_p+\cos\psi\,z_p.
\end{aligned}
}
$$

The two steps together are

$$
(x_v,y_v,z_v)
\xrightarrow{\,R_x(-\theta)\,}
(x_p,y_p,z_p)
\xrightarrow{\,R_y(-\psi)\,}
(x_w,y_w,z_w).
$$

The order cannot be swapped: the first thing to undo is pitch, which was applied last in
the forward process; yaw is undone afterwards. If we applied $R_y(-\psi)$ first, we would
rotate about the wrong axis in a coordinate frame that has not yet been restored.


## 5. From World Sphere Coordinates Back to Longitude and Latitude

This project fixes the forward relation from longitude and latitude to unit-sphere
coordinates as

$$
\boxed{
\begin{aligned}
x_w &= \cos\phi\sin\lambda,\\
y_w &= \sin\phi,\\
z_w &= \cos\phi\cos\lambda.
\end{aligned}
}
$$

Latitude is therefore recovered directly from $y_w$:

$$
\boxed{\phi=\arcsin(y_w)}.
$$

Theoretically $y_w\in[-1,1]$; the implementation still clips it first with `np.clip` to
absorb floating-point error.

Longitude is recovered from the $xz$ plane:

$$
\boxed{\lambda=\operatorname{atan2}(x_w,z_w)}.
$$

One must not use $\arctan(x_w/z_w)$: the single-argument arctangent cannot distinguish
quadrants, and it divides by zero when $z_w=0$. `atan2` uses both components and returns a
value in $(-\pi,\pi]$.

At this point, every screen pixel inside the disk corresponds to a unique
$(\phi,\lambda)$.

## 6. From Longitude and Latitude into `Frame.data`

`Frame.layer(level)` returns a 2D array of shape

$$
(n_{\mathrm{lat}},n_{\mathrm{lon}})
$$

Row 0 of the array corresponds to the northern end and row $n_{\mathrm{lat}}-1$ to the
southern end; the longitude columns start at $0^\circ\mathrm E$ and increase eastward.

### 6.1 From Longitude/Latitude to Floating-Point Array Indices

The continuous row index that corresponds to latitude is

$$
\boxed{
r=\frac{\tfrac\pi2-\phi}{\pi}(n_{\mathrm{lat}}-1)
}.
$$

It satisfies

$$
\phi=\frac\pi2\Rightarrow r=0,
\qquad
\phi=-\frac\pi2\Rightarrow r=n_{\mathrm{lat}}-1.
$$

The continuous column index that corresponds to longitude is

$$
\boxed{
c=\left(\frac{\lambda}{2\pi}n_{\mathrm{lon}}\right)
\operatorname{mod} n_{\mathrm{lon}}.
}
$$

The modulo makes the column wrap around, so the result stays valid even when
$\lambda<0$ (west of the $0^\circ$ meridian).

### 6.2 Bilinear Interpolation

Rounding directly to the nearest grid point would make the color boundaries jump while
the globe rotates. The App keeps the fractional indices and performs bilinear
interpolation (for a general implementation, see Press et al., 2007).

Let

$$
r_0=\lfloor r\rfloor,
\qquad
r_1=\min(r_0+1,n_{\mathrm{lat}}-1),
$$

$$
c_0=\lfloor c\rfloor,
\qquad
c_1=(c_0+1)\bmod n_{\mathrm{lon}},
$$

and define the fractional weights

$$
\alpha=r-r_0,
\qquad
\beta=c-c_0.
$$

Interpolate first along longitude:

$$
F_0=(1-\beta)F_{r_0,c_0}+\beta F_{r_0,c_1},
$$

$$
F_1=(1-\beta)F_{r_1,c_0}+\beta F_{r_1,c_1}.
$$

Then interpolate along latitude:

$$
\boxed{
F(\phi,\lambda)=(1-\alpha)F_0+\alpha F_1.
}
$$

Here $c_1$ uses a modulo because longitude is periodic, whereas $r_1$ uses a minimum
because latitude is not: at the poles the interpolation must stay on the last row instead
of wrapping around to the first one.

## 7. From Field Value to Color

Let the current color-scale range be $[F_{\min},F_{\max}]$. The sampled value is first
normalized to

$$
q=\operatorname{clip}\left(
\frac{F-F_{\min}}{F_{\max}-F_{\min}},0,1
\right).
$$

The color table is pre-discretized into 256 RGB values. The lookup index is

$$
k=\lfloor255q\rfloor,
$$

and the final base color is $C_k=(R_k,G_k,B_k)$.

### 7.1 Limb Shading

The $z_v$ obtained from the inverse orthographic projection also describes how far the
pixel is from the center of the sphere:

$$
z_v=1 \quad\text{at the center of the globe},
\qquad
z_v=0 \quad\text{at the limb}.
$$

The App modulates the color with the brightness function

$$
S(z_v)=0.84+0.16z_v
$$

as follows:

$$
\boxed{C_{\mathrm{shade}}=S(z_v)C_k}.
$$

The center keeps its original brightness and the limb is reduced to 84%, which gives a
slight sense of depth. This limb shading is purely a display effect.

### 7.2 Graticule and Transparent Background

The graticule (the grid of latitude and longitude lines) is drawn every $30^\circ$. The
implementation computes, for each pixel, the angular distance to the nearest multiple of
$30^\circ$ in longitude and in latitude, and blends pixels that are close enough to a
grid line with white.

Finally it builds an RGBA array: alpha 255 inside the unit circle and alpha 0 outside.

## 8. Why the Climate Field Uses Inverse Mapping but Coastlines Use Forward Projection

The climate field is a dense pixel image. Inverse mapping guarantees that every screen
pixel inside the disk gets a data value, so no holes appear.

Coastlines are sparse polylines, naturally represented as a list of longitude/latitude
points. For them the forward path is more direct:

$$
(\lambda,\phi)
\longrightarrow
(x_w,y_w,z_w)
\longrightarrow
(x_v,y_v,z_v)
\longrightarrow
(x_{\mathrm{screen}},y_{\mathrm{screen}}).
$$

where

$$
x_w=\cos\phi\sin\lambda,
\quad
y_w=\sin\phi,
\quad
z_w=\cos\phi\cos\lambda.
$$

Then yaw is applied first and pitch second, in the forward order. Only points with

$$
z_v>0
$$

lie on the visible hemisphere. Points on the back side are not added to the
`QPainterPath`, so a coastline cannot be seen "through" the globe.

`_coastline_path()` also starts a new subpath when the polyline crosses the visible
boundary or when the screen distance between consecutive points suddenly becomes too
large. This avoids drawing one long straight line between two points that are not actual
neighbors.

!!! important "Both directions must share the same conventions"

    The climate field follows the inverse path "screen → world" while the coastlines
    follow the forward path "world → screen". The two must use exactly the same axis
    directions, the same longitude/latitude definition, and the same yaw/pitch order;
    otherwise the coastlines will be misaligned with the climate field.

## 9. How Mouse Interaction Changes the Projection

The interaction itself is simple: it only changes the projection parameters, then
invalidates the cache and asks Qt to repaint.

| Action | State update | Design constraint |
|---|---|---|
| Horizontal drag $\Delta x$ | $\psi\leftarrow(\psi-0.55\Delta x)\bmod360^\circ$ | longitude may wrap around indefinitely |
| Vertical drag $\Delta y$ | $\theta\leftarrow\theta+0.45\Delta y$ | clamped to $[-85^\circ,85^\circ]$ |
| Scroll wheel | $s\leftarrow s(1+\Delta/2400)$ | zoom limited to $[0.60,1.16]$ |
| Double click | restore yaw $=0^\circ$, pitch $=12^\circ$, zoom $=0.94$ | return to the common default view |
