# 8.1 PlaSiC App Architecture Guide { #plasic-app }

This chapter is not a line-by-line tutorial for `plasic_app`. It is a **code map** that you can return to when you customize the app.

!!! tip "Remember this sentence"

    `MainWindow` coordinates the workflow, configuration objects describe intent, the controller manages external processes,
    `RunManager` writes the experiment to disk, and the visualization layer consumes parsed `Frame` objects.

## 1. Where the App fits in the repository

PlaSiC has two clearly separated parts:

- `src/` is the standalone C11 numerical core. It performs the actual climate-model calculations.
- `plasic_app/` is the PySide6 desktop front end. It configures, builds, starts, monitors, and visualizes model runs.

The user interface uses Qt for Python (PySide6; Qt Group, n.d.).

The App does not embed the C model in the Python process. It starts the C executable as a child process with command-line options derived from the Python configuration and receives results through files in the run directory. This boundary lets the two parts be tested independently. The same C executable can run from a terminal or be started by the desktop App.

## 2. Layer map: what each directory does

The modules under `plasic_app/src/plasic_app/` can be read as six layers:

| Layer | Main files | Responsibility |
|---|---|---|
| Entry point | `__main__.py`, `app.py` | Create `QApplication`, apply the theme, create `MainWindow`, and enter the Qt event loop |
| UI orchestration | `ui/main_window.py` | Assemble the interface, connect signals, coordinate build/run, and poll output |
| Forms and metadata | `ui/parameter_form.py`, `config/catalog.py`, `resources/*.json` | Generate controls from the parameter catalog; provide variable labels, units, color scales, and related metadata |
| Domain configuration | `config/models.py` | Represent and validate build, run, and visualization settings; convert them to the C runtime configuration |
| Run control | `controller/commands.py`, `controller/process_controller.py`, `controller/process_wrapper.py` | Build commands, run them asynchronously with `QProcess`, and manage stopping and logs |
| Runs and data | `runs/manager.py`, `protocol/*.py`, `visualization/*.py` | Create reproducible experiment directories, read progress and field data incrementally, and draw results |

## 3. What happens at startup

The program entry point is intentionally small:

```text
python -m plasic_app
  └─ __main__.py
      └─ app.main()
          ├─ Create QApplication
          ├─ Set Fusion style, fonts, and a light palette
          ├─ Create and show MainWindow
          └─ application.exec() enters the Qt event loop
```

`MainWindow.__init__()` is the App's assembly point. It:

1. Calls `discover_c_root()` to find the C-model directory that contains the `Makefile`.
2. Loads `ParameterCatalog` and `VariableCatalog`.
3. Creates `RunManager` and `ProcessController`.
4. Initializes the current build, current run, incremental readers, and frame buffer.
5. Builds the UI and connects Qt signals to slots.
6. Starts a `QTimer` with a 150 ms interval. The timer calls `_poll_outputs()` periodically.

!!! note "Concurrency model"

    The App does not run expensive calculations in the GUI thread. External processes managed by `QProcess` perform the build and model run; the GUI thread only handles events and reads a bounded amount of new output. Each poll reads at most 128 field frames. This is an important back-pressure limit that prevents a long data stream from using all memory or blocking the interface.

## 4. The most important data structures

### 4.1 `ExperimentConfig`: the top-level intent of one experiment

`config/models.py` represents the App's domain configuration with four dataclasses:

```text
ExperimentConfig
├─ build: BuildConfig
│  ├─ resolution / atmosphere_levels
│  ├─ mpi_enabled / mpi_processes
│  └─ c_compiler / mpi_compiler / mpi_launcher
├─ run: RunConfig
│  ├─ steps / calendar / start_year / start_yday
│  ├─ start_hour / start_minute / reset_nstep
│  ├─ co2_forcing / restart / data_dir
│  └─ frame_interval / progress_interval
└─ visualization: VisualizationConfig
   ├─ buffer_frames / auto_levels (color-scale limits)
   └─ view_mode / selected_variable / selected_level
```

This grouping reflects three different change costs:

- A change to `BuildConfig` usually requires a new C build artifact.
- A change to `RunConfig` usually requires only a new run directory.
- A change to `VisualizationConfig` changes only how the App buffers or displays data.

Here, `auto_levels` controls the color scale range used by field views. When it is enabled, the lower and upper color limits are recomputed from the current field and viewing scope. When it is disabled, the view uses a fixed or manually entered range, so colors remain comparable across time steps.

`BuildConfig.build_key()` computes a stable hash of the complete build configuration. The build directory name includes the resolution, number of levels, MPI settings, and this key, so different build configurations cannot accidentally reuse the same `plasic.x`.

`ExperimentConfig.c_runtime_config()` is the translation step between the Python-side settings and the C model's inputs. The flow is:

1. The form values are collected into `ExperimentConfig` and its `RunConfig`.
2. `c_runtime_config()` resolves paths and returns the values that the C model needs, such as the output file, frame interval, and CO₂ forcing file.
3. `run_invocation()` converts those values into command-line arguments such as `--output`, `--frame-interval`, and `--co2-forcing`, then starts `plasic.x` through the process wrapper.

For example, changing `RunConfig.frame_interval` changes the value returned by `c_runtime_config()` and the argument passed to `plasic.x`.

### 4.2 Catalogs: describe how values are shown; they do not store current values

Two built-in JSON files provide declarative metadata:

- `resources/parameters.json`
- `resources/variables.json` 

For example, an entry in `parameters.json` can define the horizontal-resolution control:

```json
{
  "name": "resolution",
  "label": "Horizontal resolution",
  "type": "enum",
  "default": "T42",
  "choices": ["T21", "T31", "T42", "T85"],
  "section": "Build",
  "phase": "compile",
  "component": "dynamics",
  "description": "Spectral truncation and Gaussian grid: T21=64×32, T31=96×48, T42=128×64, T85=256×128."
}
```

This metadata tells `ParameterForm` to create a drop-down list in the Build section. It also tells the configuration layer which value to use by default and that the setting belongs to the compile phase.

An entry in `variables.json` describes a field that the model can output and that the viewer can display:

```json
{
  "id": 1,
  "name": "air_temperature",
  "label": "Air temperature",
  "unit": "K",
  "dimensions": ["level", "latitude", "longitude"],
  "component": "atmosphere",
  "colormap": "CET-L4"
}
```

Here, the protocol uses `id` and `name` to identify the field, while the visualization layer uses `label`, `unit`, `dimensions`, and `colormap` to present it correctly. The two files therefore describe different things: `parameters.json` describes controls for configuring a run, whereas `variables.json` describes data fields for interpreting and displaying model output.

`ParameterCatalog` and `VariableCatalog` load these JSON files and provide lookup methods. The current parameter values are not stored in a catalog. They live in the controls created by `ParameterForm`, and `MainWindow._configuration()` collects them into an `ExperimentConfig`.

!!! warning "A common mistake"

    Adding an item only to `parameters.json` usually makes it visible to the form. If it belongs to `BuildConfig` or `RunConfig`, you must also update the relevant dataclass, validation, command construction, or C-runtime mapping. The metadata and domain model must stay consistent.

### 4.3 Invocations: immutable descriptions of commands

`BuildInvocation` and `RunInvocation` are dataclasses with `frozen=True`. They store:

- the `program` to execute;
- its `arguments`;
- the `working_directory`;
- an independent `environment`;
- and, for a build invocation, the expected `executable` path.

They **describe commands but do not execute them**. `commands.py` translates configuration into an invocation, and `ProcessController` executes it. This separation allows command generation to be tested and inspected independently of the Qt process lifecycle.

### 4.4 `PreparedRun`: the on-disk handle for one run

`RunManager.prepare()` validates the configuration, creates a unique run directory, prepares a restart file, and returns an immutable `PreparedRun`:

```text
PreparedRun
├─ run_id
├─ directory
├─ initial_restart (None for a cold start)
├─ progress  -> progress.txt
├─ frames    -> frames.pstream
└─ log       -> model.log
```

`PreparedRun` stores the run directory and its key paths. It does not store a separate runtime-configuration file: the C runtime options are assembled later as command-line arguments.

### 4.5 `Frame` and `FrameBuffer`: the data actually consumed by visualization

`protocol/pstream.py` parses the binary frames written by the C side into immutable `Frame` objects. Important fields include the variable ID and name, unit, simulation time, level index, minimum and maximum values, and a `float32` NumPy array with shape `(layers, nlat, nlon)` (NumPy; Harris et al., 2020).

`FrameBuffer` uses `dict[str, deque[Frame]]` internally. Each variable has its own bounded queue. When the user changes the variable or vertical level, the interface can redraw the latest buffered frame without rereading the whole file.

The stream-file header also declares the number of deep-ocean levels (`ocean_levels`). Variables listed in the catalog but unavailable in the current run—for example, deep-ocean temperature and salinity when the model was not built with a three-dimensional ocean—are disabled with an explanation. If a selected variable is not present in the stream, the interface clears the old image and explains the situation instead of showing the previous variable's result as if it were current.

## 5. The core call chains

### 5.1 Clicking “Start Run”

<div class="arch-steps" aria-label="Call sequence after clicking Start Run">
  <div><b>1</b><span><strong>MainWindow</strong><small>Collect and validate an ExperimentConfig from the form</small></span></div>
  <div><b>2</b><span><strong>build_invocation()</strong><small>Locate the `plasic.x` for this configuration; start an asynchronous build if it is missing</small></span></div>
  <div><b>3</b><span><strong>RunManager.prepare()</strong><small>Create the run directory, write the configuration record, and return PreparedRun</small></span></div>
  <div><b>4</b><span><strong>run_invocation()</strong><small>Create the complete launch command for the wrapper, MPI, and `plasic.x`</small></span></div>
  <div><b>5</b><span><strong>ProcessController.start_run()</strong><small>Start the external model with QProcess and manage its log and lifecycle</small></span></div>
  <div><b>6</b><span><strong>C11 PlaSiC</strong><small>Append records to `progress.txt` and `frames.pstream`</small></span></div>
</div>

Two design details are easy to miss:

1. If the target build does not exist when the user starts a run, `pending_run=True` lets the App continue with the run automatically after a successful build.
2. The form may change while the build is running, so `_build_finished()` reads and validates the current configuration again.

The run command does not always start `plasic.x` directly. `run_invocation()` first starts `controller.process_wrapper`. The wrapper creates an independent session and then uses `execvpe()` to replace itself with the actual command. In MPI mode, `mpirun -np N` is placed before that command. This lets Stop terminate the complete process group instead of only the outer Python process.

### 5.2 How live output returns to the interface

<div class="arch-stream" aria-label="Live data flow from the C model back to the interface">
  <div class="arch-stream__source"><strong>plasic.x</strong><small>Appends output continuously</small></div>
  <div class="arch-stream__lane">
    <span class="arch-node"><code>progress.txt</code></span><span class="arch-arrow">→</span>
    <span class="arch-node"><code>ProgressTail</code></span>
  </div>
  <div class="arch-stream__lane">
    <span class="arch-node"><code>frames.pstream</code></span><span class="arch-arrow">→</span>
    <span class="arch-node"><code>PStreamReader</code></span>
  </div>
  <div class="arch-stream__merge"><span>QTimer every 150 ms</span><strong>MainWindow._poll_outputs()</strong></div>
  <div class="arch-stream__result">
    <span><code>FrameBuffer</code></span><span class="arch-arrow">→</span>
    <span><code>LiveFieldView</code></span><span class="arch-arrow">→</span>
    <span>2D map · globe · global mean</span>
  </div>
</div>

`ProgressTail` stores a byte offset and an incomplete final line. It returns only new, complete JSON events (the JSON exchange format is specified by Bray, 2017).
`PStreamReader` also stores an offset. It advances only after the file header, frame header, payload, and FNV-1a checksum have all passed validation. If the C process is writing a partial frame, the reader stops for this poll and retries that frame from the same position on the next poll.

These incremental readers are the protocol boundary between the App and files that continue to grow. If you change the C-side output format, inspect `protocol/progress.py` or `protocol/pstream.py` as well as the plotting code.

## 6. Each run directory is a reproducible experiment record

The default run root is `plasic_app/runs/`. A successfully prepared experiment contains roughly:

```text
runs/<timestamp>-<uuid>/
├─ config.json          # Complete ExperimentConfig at the App layer
├─ initial.restart      # Optional; hard link preferred, copy used as a fallback
├─ model.log            # stdout / stderr from the child process
├─ progress.txt         # Structured progress records
├─ frames.pstream       # Live or replayable field-data stream
├─ monthly/             # Monthly model output
└─ final.restart        # Final model state
```
