# 1.1 Running PlaSiC first!

This note answers two questions:

1. **How do I compile the C sources in `src/` into an executable and launch one integration?**
2. **What does the Makefile do during a build, and how do I run common configuration experiments with the smallest possible edit?**

The sources are an independent C implementation of the PlaSim model (Fraedrich et al., 2005).

No previous Makefile experience is assumed: every construct used below is explained where it first appears. After reading this note and following along once, you should be able to:

- carry out a complete "cold start → integration → restart output" cycle on your own;
- understand the compile and run commands that `make` actually executes;
- adjust resolution, vertical levels, MPI process count, integration length, the CO₂ setup, and output directories for an experiment;
- wire a newly added `.c` file into the build system correctly.

## 1. A complete build and run

### 1.1 What you need before running

| Dependency | Purpose | Required |
|---|---|---|
| C compiler (`cc` / `clang` / `gcc`) | compile the C11 sources | yes |
| [SHTns](https://nschaeff.bitbucket.io/shtns/) | spherical-harmonic transforms | yes |
| FFTW3 | fast Fourier transform backend used by SHTns | yes |
| NetCDF-C | read surface boundary data, write monthly-mean results | yes |
| LAPACK | matrix inversion (macOS uses the Accelerate framework directly) | yes |
| Open MPI (`mpicc`, `mpirun`) | compiling and launching MPI builds | required for parallel runs |
| `pkg-config` | locate library headers and link flags automatically | recommended |

For complete macOS installation instructions — in particular building and installing SHTns 3.7.5 and setting `SHTNS_PREFIX` — see the "Build dependencies" section of `README.md` at the repository root. The transform library is SHTns (Schaeffer, 2013), whose FFT backend is FFTW (Frigo & Johnson, 2005); surface data and monthly output use NetCDF (Rew & Davis, 1990); matrix inversion uses LAPACK (Anderson et al., 1999); and parallel builds use Open MPI (Gabriel et al., 2004). One thing is worth remembering here: **the Makefile locates these libraries through `pkg-config` or `SHTNS_PREFIX`**. If it cannot find them, compilation fails with an error such as a missing `shtns.h`.

!!! note "Python is not a runtime dependency"

    Python is used only by the test targets in the Makefile; `plasic.x` itself does not depend on Python.

### 1.2 Building

If you have never built a C program before, the short version is: each `.c` file is compiled into an **object file** (`.o`) that holds machine code and a table of symbols; related object files are packed into a **static library** (`.a`); and the remaining object files plus that library are **linked** into an **executable** (`plasic.x`). The Makefile drives the whole chain, so in practice you only need the commands below.

From the project root, run:

```bash
make -C src          # incremental build: recompile only what needs updating
```

`-C src` tells make to change into `src/` before reading the Makefile, so every path in its rules is relative to `src/`. The first build compiles every source file and therefore takes a while; afterwards, editing one `.c` file recompiles only the affected files and relinks.

To check the code more strictly (treating warnings as errors), run:

```bash
make -C src strict   # delete all build products, then rebuild everything with -Werror
```

!!! warning "`strict` runs `clean` first"

    The prerequisites of `strict` are `clean all`, so it deletes the entire `build/` and `run/` trees first (see the `clean` row in Section 3.4) — **including any run results already there**. Make sure you have nothing to keep before using it.

!!! note "What happens between a `.c` file and an executable"

    A C build is a chain of four stages, driven by the compiler wrapper (`cc`, `clang`, or `gcc`):

    1. **Preprocessing** — `#include` headers are pulled in and `#define` / `-D` macros are expanded;
    2. **Compilation** — each `.c` file is translated into machine code and stored in an **object file** (`.o`) together with the symbols it defines and those it still needs; the `-c` flag stops the chain here;
    3. **Archiving** — related object files are collected into a **static library** (`.a`), which is merely a container of object files; this project's core library is `libplasic.a`;
    4. **Linking** — object files and libraries are combined into an **executable** (`plasic.x`); any symbol that cannot be resolved is a link error.

    This is why Makefile rules talk about `.o` files: an object file is the smallest reusable unit of a build.

A successful build produces two main artifacts:

| Artifact | Path | Description |
|---|---|---|
| Static library | `build/T31_L13_MPI_P2_O16/libplasic.a` | archive of the dynamical-core, parameterization, state, and I/O object files |
| Executable | `build/T31_L13_MPI_P2_O16/plasic.x` | final entry point of the model |

In the directory name `T31_L13_MPI_P2_O16`, T31 is the spectral truncation wavenumber, L13 is the number of vertical levels, MPI_P2 is two MPI processes, and O16 is 16 deep-ocean levels; Section 3.2 derives the name. The `.x` suffix is merely this project's convention for the executable.

### 1.3 Running

The simplest way to run the model is to let the Makefile build first and then launch it:

```bash
make -C src run                # integrate 100 steps by default
make -C src run STEPS=3650     # override the step count
```

`make run` performs the following steps (commands run inside `src/`, so all paths are relative to `src/`):

```text
make run
├─ prerequisite all: ensure plasic.x is up to date for the current configuration
├─ mkdir -p ../run/T31_L13_MPI_P2_O16
├─ choose the initial condition:
│    RESTART non-empty                            → continue from the file RESTART names
│    RESTART empty but run/<config>/status exists → continue automatically from that status file
│    neither                                      → pass no --restart; cold start from surface data
└─ mpirun -np 2 ../build/T31_L13_MPI_P2_O16/plasic.x \
       [--restart ../run/T31_L13_MPI_P2_O16/status] --steps 100 \
       --co2-forcing data/forcing/CO2/....csv \
       --progress ../run/T31_L13_MPI_P2_O16/progress.txt \
       --progress-interval 1 \
       --output ../run/T31_L13_MPI_P2_O16/status
```

The `....csv` above abbreviates the default `CO2_FORCING` path; its full value is defined in `src/Makefile`. `mpirun -np 2` starts the executable as two MPI processes, and the count must match the `NPRO` used at compile time (Section 1.4). Besides `status`, the run also writes `progress.txt`, a JSON progress log.

About cold starts and continuations:

- **Cold start**: no restart file is used. The model starts from the NetCDF surface fields in `--data-dir` (default `data/surface`, relative to `src/`); the eight fields of that directory and their monthly layout are documented in [6.5 Cold-Start Surface Boundary Fields at T42](../6-experiments/6.5-cold-start-surface-fields-t42.md). By default CO₂ is read from a monthly CSV on 15° latitude bands under `data/forcing/CO2/`.
- **Continuation**: whenever `run/<config>/status` exists, `make run` automatically uses it as input. To opt out, point `RUN_DIR` at a fresh directory, for example `make -C src run RUN_DIR=../run/smoke`.

!!! warning "`--co2-forcing` and `--co2-ppm` are mutually exclusive"

    The model accepts exactly one of two CO₂ settings: `--co2-ppm PPMV` (one concentration for the whole field) or `--co2-forcing FILE` (monthly external forcing on 15° latitude bands). Passing neither, or both, is a fatal error. `make run` uses the external forcing by default; setting `CO2_PPM` switches it to a fixed concentration (see Section 3.1).

### 1.4 Running the executable directly

`plasic.x` is a standalone command-line program; you can invoke it without `make run`. From inside `src/`, for example:

```bash
mkdir -p ../run/demo
../build/T31_L13_MPI_P2_O16/plasic.x \
  --data-dir data/surface \
  --co2-forcing data/forcing/CO2/mole-fraction-of-carbon-dioxide-in-air_input4MIPs_GHGConcentrations_CMIP_UoM-CMIP-1-2-0_gn-15x360deg_000001-201412.csv \
  --steps 32 \
  --output ../run/demo/status
```

The CO₂ file is the CMIP6 historical greenhouse-gas concentration dataset (input4MIPs; Eyring et al., 2016; Meinshausen et al., 2017).


!!! note "The program does not create directories"

    `plasic.x` only computes and writes files; it never creates parent directories. When invoking it directly, run `mkdir -p` first, as in the examples above (`make run` and `make historical` already do this for you).

`plasic.x --help` prints all command-line options; the common ones are listed below.

| Option | Effect |
|---|---|
| `--config FILE` | read run options from a JSON file (lower precedence than the command line) |
| `--restart FILE` | continue from a restart file; omit for a cold start |
| `--data-dir DIR` | surface-data directory for cold starts; default `data/surface` |
| `--steps N` | number of integration steps; **mandatory** and must be ≥ 1 |
| `--output FILE` | where to write the final restart; default `status` |
| `--co2-forcing FILE` / `--co2-ppm PPMV` | CO₂ forcing mode; exactly one of the two is required |
| `--monthly-output DIR` | write monthly-mean NetCDF output (the directory must already exist) |
| `--progress FILE`, `--progress-interval N` | append one JSON progress record to FILE every N steps |
| `--frames FILE`, `--frame-interval N` | write binary frames for the desktop app every N steps |
| `--calendar gregorian\|360day` | calendar kind for a cold start (default `gregorian`) |
| `--start-year`, `--start-yday`, `--start-hour`, `--start-minute` | cold-start date (default year 0, day-of-year 1, 00:00); the time must land on a step boundary |
| `--reset-nstep N` | warm start only: replace the `nstep` read from the restart and print the new model date |
| `--dynamics-only` | integrate the dynamical core only, skipping the physical parameterizations |

Option precedence is **command line > JSON configuration file > code defaults**: the first pass of `plasic_cli_run()` reads only `--config`, and the second pass overwrites options one by one. The old date options `--start-month`, `--reset-calendar`, and `--end-year` no longer exist; see [5.1 Calendar](../5-time-control/5.1-calendar.md) for the current time model.

## 2. Makefile basics: think in recipes

### 2.1 Rules, targets, and prerequisites

A Makefile describes what depends on what and how each thing is produced. Its smallest unit is a **rule**:

```make
target: prerequisite1 prerequisite2
	command that produces the target
```

The link rule in this project is an example:

```make
$(PROGRAM): $(RUNTIME_OBJECTS) $(LIBRARY)
	$(CC) $(CFLAGS) $(LDFLAGS) -o $@ $(RUNTIME_OBJECTS) $(LIBRARY) $(LDLIBS)
```

Read it as: "the executable `plasic.x` depends on several runtime object files and a static library; whenever any prerequisite is newer than `plasic.x`, run the link command below to regenerate it." The command line must begin with **one tab character**, not spaces — the most common beginner mistake in Makefiles.

make itself knows nothing about C: it only compares file timestamps, so a rule is really a recipe guarded by file times. Its working order is:

1. Start from the target named on the command line (if none is given, from the default goal — `all` here);
2. Inspect each prerequisite recursively: if it does not exist, or is newer than the target, update it first;
3. Once all prerequisites are handled, decide whether the target itself must be rebuilt and, if so, run the rule's commands.

This is where incremental compilation comes from: after you edit one `.c` file, only its `.o` file, the static library, and the executable are regenerated; all other object files are reused unchanged.

### 2.2 Variables

Makefile variables avoid repetition:

```make
CC ?= cc          # ?= assigns a default only if CC is not already defined,
CFLAGS ?= -O2     #    so the command line can override it: make CFLAGS=...
CFLAGS += -std=c11 -fno-fast-math   # += appends to the existing value
```

Variables are referenced as `$(name)`. `?=` supplies a "default that callers may override", `+=` appends to the current value, and the two are often used together. `$(shell ...)` is a make **function**: it runs a shell command and returns its output; this project uses it to compute the spectral truncation.

### 2.3 Automatic variables

The commands in a rule can use automatic variables. This project uses three of them:

| Form | Meaning |
|---|---|
| `$@` | the current rule's target |
| `$<` | the first prerequisite |
| `$^` | all prerequisites (deduplicated) |

### 2.4 Pattern rules

Writing one compile rule per source file would be impossible to maintain with more than a hundred sources. A **pattern rule** uses `%` as a wildcard:

```make
$(BUILD_DIR)/%.o: %.c
	@mkdir -p $(dir $@)
	$(CC) $(CPPFLAGS) $(CFLAGS) $(WARNFLAGS) -MMD -MP -c $< -o $@
```

`%` matches any path fragment, so `tools/foo.c` compiles to `build/.../tools/foo.o` and `dynamical_core/bar.c` to `build/.../dynamical_core/bar.o`. The rule does three things at once:

- `@mkdir -p $(dir $@)`: create the target directory if it does not exist (the leading `@` stops make from printing the command itself);
- `-c $< -o $@`: compile without linking, turning the `.c` file into a `.o` file;
- `-MMD -MP`: in addition to the `.o` file, have the compiler write a small `.d` text file that records which headers the source includes; `-MP` protects that record against headers that are later deleted. The `-include` directive at the end of the Makefile reads these `.d` files back, so **editing a header also triggers recompilation** of the affected objects.


### 2.5 Phony targets and conditionals

`.PHONY` declares targets that do not correspond to real files:

```make
.PHONY: all clean strict run historical historical-run test test-data test-runtime
```

Without this declaration, a file named `clean` sitting in the directory would make `make clean` look "already up to date" and do nothing. Conditionals (`ifeq` / `else` / `endif`) choose different branches based on the user's configuration — for example whether to use the MPI compiler or whether to enable the three-dimensional ocean.

### 2.6 Debugging a Makefile

- `make -p`: dump make's internal variable and rule database (very long; pipe it through `grep`);
- temporarily add `@echo "VAR = $(VAR)"` to a rule to print intermediate values.

## 3. Reading this project's Makefile

Open `src/Makefile` and you will see a conspicuous line of `=` characters splitting the file in two:

```text
user-configurable variables   ← everyday experiments change only this part
============================
build implementation          ← derived variables, source lists, and rules
```

### 3.1 User-configurable variables (top half)

| Variable | Default | Purpose |
|---|---|---|
| `CC` / `AR` | `cc` / `ar` | compiler and static-library archiver; with `MPI=1`, `CC` is replaced by `MPI_CC` |
| `NLAT` | `48` | number of latitude rows (Gaussian grid), which fixes the horizontal resolution and time step |
| `NLEV` | `13` | number of vertical (σ) levels |
| `NPRO` | `2` | MPI process count / spectral-space partitions; serial builds (`MPI=0`) must set it to `1` |
| `OCEAN_MODEL` | `3d` | ocean backend: `3d` for the deep three-dimensional ocean, `slab` for the single-layer mixed layer |
| `DEEP_OCEAN_LEVELS` | `16` | vertical levels of the three-dimensional ocean |
| `MPI` | `1` | `1` uses real MPI (`mpicc` / `mpirun`), `0` uses the serial backend |
| `MPI_CC` / `MPIRUN` | `mpicc` / `mpirun` | MPI compiler and launcher |
| `BUILD_ROOT` / `RUN_ROOT` | `../build` / `../run` | root directories for build and run products |
| `BUILD_DIR` / `RUN_DIR` | auto | build/run directory for the current configuration; may be overridden wholesale |
| `STEPS` | `100` | number of integration steps for `make run` |
| `PROGRESS_INTERVAL` | `1` | how often `make run` appends a progress record; increase it to shrink `progress.txt` on long runs |
| `RESTART` | empty | restart file to continue from; when empty, `$(RUN_DIR)/status` is used automatically if it exists |
| `CO2_PPM` / `CO2_FORCING` | empty / built-in CSV | CO₂ setting for `make run`; when `CO2_PPM` is set, the fixed concentration wins |
| `CFLAGS` | `-O2` | optimization level; `strict` appends `-Werror` |
| `SHTNS_PREFIX` | empty | SHTns installation prefix; when empty, `pkg-config` is used |


### 3.2 Derived parameters: where T31 and `_O16` come from

The bottom half first converts user parameters into derived variables; the three key ones are:

```make
TRUNCATION = $(shell expr \( $(NLAT) \* 2 - 1 \) / 3)
OCEAN_BUILD_SUFFIX = $(if $(filter 3d,$(OCEAN_MODEL)),_O$(DEEP_OCEAN_LEVELS),)
BUILD_DIR ?= $(BUILD_ROOT)/T$(TRUNCATION)_L$(NLEV)$(MPI_BUILD_SUFFIX)$(OCEAN_BUILD_SUFFIX)
```

Keeping different resolutions in different build directories is deliberate: the grid dimensions, spectral-space size, and three-dimensional ocean array layout are all fixed **at compile time**, so mixing `.o` files from an old directory can produce memory errors that are very hard to notice.

The compile-time parameters then become C preprocessor macros through `-D`:

```make
CPPFLAGS += -DPLASIC_NLAT=$(NLAT) -DPLASIC_NLEV=$(NLEV) -DPLASIC_NPRO=$(NPRO)
CPPFLAGS += -DPLASIC_DEEP_NLEV=$(DEEP_OCEAN_LEVELS)
CPPFLAGS += -DPLASIC_USE_MPI=$(MPI)
```


### 3.3 Source lists and the static library

The Makefile groups sources into two lists:

| List | Contents | Destination |
|---|---|---|
| `KERNEL_SOURCES` | dynamical core, physical parameterizations, state management, I/O tools | compiled and packed into `libplasic.a` |
| `RUNTIME_SOURCES` | runtime main loop, initialization, output, and `main` | linked directly into the final program |

Object-file paths are produced by pattern substitution:

```make
KERNEL_OBJECTS = $(KERNEL_SOURCES:%.c=$(BUILD_DIR)/%.o)
```

that is, `tools/calmod_kernels.c` → `build/T31_.../tools/calmod_kernels.o`. The static library is created with `ar rcs` (insert the object files, create the archive if needed, write a symbol index); the final program links `RUNTIME_OBJECTS` together with `libplasic.a`.

### 3.4 Main targets

| Target | Effect |
|---|---|
| `all` (default) | build `plasic.x` |
| `strict` | clean, then rebuild everything with `-Werror` |
| `run` | build and run one standard integration |
| `historical` | build and run the 1850–2014 historical experiment (requires `INITIAL_CONDITION=...`; see [6.2 Historical experiment](../6-experiments/6.2-historical-experiment-1850-2014.md)) |
| `clean` | delete all build and run products |

With this much understood, you have the build knowledge needed to design model experiments of your own. Next, read [1.2 A time step in pseudocode](1.2-pseudocode-for-one-time-step.md) to see what the model actually does inside a time step.
