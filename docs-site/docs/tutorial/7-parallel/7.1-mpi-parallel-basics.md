# 7.1 MPI Parallel Basics { #mpi }

This chapter is written for readers who have no MPI (Message Passing Interface) experience at all.
When you finish reading it, you should be able to answer three questions:

1. What problem MPI solves in a climate model;
2. How PlaSiC wraps MPI into one uniform set of `mp_*` interfaces;
3. What every function in the `src/mpi/` directory actually does during a single run of the model.


---

## 1. From One Process to Many Processes

### 1.1 Why climate models need parallelism

One time step of PlaSiC performs three expensive jobs:

1. At every latitude–longitude grid point in **grid space**, it computes nonlinear products and physical parameterizations;
2. In **spectral space**, it solves the semi-implicit equations and performs diffusion and time stepping;
3. Between the two, it repeatedly applies spherical harmonic transforms.

Let the number of latitude grid points be `NLAT` and the number of vertical levels be `NLEV`.
The amount of grid-point state data per process is roughly proportional to
`NLAT × NLAT × NLEV`. If the resolution doubles, both memory and computation grow by about a
factor of eight. To run high-resolution experiments that are closer to the real Earth, the same
computation must be divided among several processors (CPU cores or compute nodes) that work on
it together.

### 1.2 Two worldviews of parallel computing

There are two mainstream parallel computing models:

| Model | Memory | Typical technology | Communication |
|---|---|---|---|
| Shared memory | All threads share one address space | OpenMP, Pthreads | Read and write the same variables directly |
| Distributed memory | Each process has its own address space | MPI | Explicitly send/receive messages |

PlaSiC uses the **distributed-memory** model: it launches several processes, each responsible for
one part of the global grid, and processes exchange data only through MPI messages. In the SHTns
build configuration, the project disables SHTns's internal OpenMP by default, precisely to keep
MPI processes and OpenMP threads from fighting over the CPU.

### 1.3 SPMD: Single Program, Multiple Data

The most typical execution model for MPI programs is **SPMD (Single Program, Multiple Data)** (Darema et al., 1988):

```text
Process 0 ─┐
Process 1 ─┤  run the same plasic.x
Process 2 ─┤  but use the rank to decide "which piece I work on"
Process 3 ─┘
```

In other words, **the same executable is launched multiple times**. The code has no separate
"entry point for process 1" and "entry point for process 2"; instead, one number (the rank)
identifies each process, and branches or loop ranges vary with that rank. Patterns like this
appear throughout PlaSiC:

```c
if (mp_is_root()) {
    /* Input/output performed only by process 0 */
}
```

and like this:

```c
const size_t rank_offset = (size_t)mp_rank() * (size_t)PLASIC_NSPP;
```

These two lines capture the whole spirit of SPMD: **one program, divided by identity.**

## 2. The Minimal Set of MPI Concepts

The authoritative definitions of every function and semantic below are in the MPI standard
(MPI Forum, 2015); the textbook treatment followed in this chapter is Gropp et al. (2014).

### 2.1 Processes, ranks, and communicators

| Term | Meaning |
|---|---|
| Process | An independent program instance with its own memory |
| Rank | The number of a process inside a communicator, starting from 0 |
| Size | The total number of processes in a communicator |
| Communicator | A group of processes that are allowed to communicate with one another |
| Root rank | The process given a special role, usually rank 0 |

`MPI_COMM_WORLD` is the largest communicator, created automatically when MPI starts, and it
contains every process. The PlaSiC native backend saves it as `active_world` right at the start:

```c
static MPI_Comm active_world = MPI_COMM_NULL;
/* in mpi_native_start(): */
active_world = MPI_COMM_WORLD;
```

### 2.2 A minimal runnable example

Without looking at PlaSiC yet, consider a complete MPI program:

```c
#include <mpi.h>
#include <stdio.h>

int main(int argc, char **argv)
{
    int rank;
    int size;

    MPI_Init(&argc, &argv);                  /* start the MPI environment */
    MPI_Comm_rank(MPI_COMM_WORLD, &rank);    /* who am I */
    MPI_Comm_size(MPI_COMM_WORLD, &size);    /* how many processes in total */

    printf("Hello from rank %d of %d\n", rank, size);

    MPI_Finalize();                          /* shut down the MPI environment */
    return 0;
}
```

On a machine with Open MPI installed (Gabriel et al., 2004):

```bash
mpicc hello.c -o hello
mpirun -np 4 ./hello
```

You will see four lines of output. Note that **the order of the output is nondeterministic**,
because the processes never agree on who prints first.

The correspondence between the three pieces of information in this small program and PlaSiC:

| Quantity in the example | PlaSiC wrapper |
|---|---|
| `rank` | `mp_rank()` |
| `size` | `mp_size()` |
| `rank == 0` | `mp_is_root()` |
| `MPI_Init` / `MPI_Finalize` | `mp_start()` / `mp_stop()` |

### 2.3 Collective and point-to-point communication

MPI communication operations fall into two broad categories.

**Collective communication** has the following characteristics:

- **Every process in the communicator must call** the same operation;
- The **order of calls must be identical** across processes; MPI uses this order to match the operations of different processes;
- Common operations include broadcast, reduce, gather, and so on.

PlaSiC uses only three kinds of collective communication: broadcast, global reduction by
element-wise summation, and gathering.

**Point-to-point communication** is a directed message between two processes. It requires
specifying the sender, the receiver, the amount of data, the data type, and a tag. Tags
distinguish different message streams on the same link. PlaSiC uses point-to-point communication
only for latitude halo exchange.

### 2.4 Blocking, deadlock, and `MPI_Sendrecv`

The most basic send/receive calls, `MPI_Send` / `MPI_Recv`, are **blocking**: the sender waits
until the buffer is available, and the receiver waits until the data actually arrives. The
following "wait for each other" code deadlocks forever:

```c
/* Wrong: both processes receive first and then send, so neither ever sends */
if (rank == 0) {
    MPI_Recv(..., /* from */ 1, ...);
    MPI_Send(..., /* to */   1, ...);
} else {
    MPI_Recv(..., /* from */ 0, ...);
    MPI_Send(..., /* to */   0, ...);
}
```

The solution is to combine "send" and "receive" into one atomic operation, `MPI_Sendrecv` (Gropp et al., 2014):

```c
MPI_Sendrecv(sendbuf, sendcount, sendtype, dest, sendtag,
             recvbuf, recvcount, recvtype, source, recvtag,
             comm, &status);
```

It sends to `dest` and receives from `source` at the same time, and MPI performs the matching
internally, so two processes cannot end up waiting for each other. PlaSiC's latitude halo
exchange (`mp_exchange_latitude_halo()`) is implemented with exactly this routine.

### 2.5 Data types and return codes

MPI is a strongly typed interface: every call must state what the data type is in C. PlaSiC uses
only two:

| C type | MPI type | Use |
|---|---|---|
| `float` | `MPI_FLOAT` | All physical fields and spectral coefficients |
| `int32_t` | `MPI_INT32_T` | Metadata, status codes, process counts |

Almost every MPI routine returns an `int` status code, where `MPI_SUCCESS` (usually 0) means
success. The PlaSiC native backend returns these status codes upward unchanged, and the `mp_*`
interface layer and its callers check them.

## 3. PlaSiC's MPI Interface Layer

### 3.1 Directory structure

`src/mpi/` contains only six files, with a very clear division of responsibilities:

```text
src/mpi/
├── plasic_mpi.h            unified public interface (facade), depends only on <stdint.h>
├── plasic_mpi.c            dispatches to a concrete backend according to PLASIC_USE_MPI
├── mpi_serial_backend.h    single-process backend interface
├── mpi_serial_backend.c    single-process backend implementation (no-ops/direct copies)
├── mpi_native_backend.h    MPI backend interface
└── mpi_native_backend.c    the real MPI implementation (the only file that includes <mpi.h>)
```

### 3.2 Facade pattern: the `mp_*` interface

The separation below is an application of the Facade pattern (Gamma et al., 1994): the rest of
the model sees only the small `mp_*` surface, not the backend that implements it.

`plasic_mpi.h` is
**the only parallel interface the entire model is allowed to use**. All other parts of the model
(`runtime/`, `physics/`, `math_tools/`, `tools/`) include only this header and never include
`<mpi.h>` directly.

The unified interface comes in four groups:

```text
Lifecycle:         mp_start, mp_stop
Identity & layout: mp_rank, mp_size, mp_is_root, mp_local_offset
Collectives:       mp_broadcast_integer, mp_broadcast_real, mp_allreduce_real,
                   mp_allgather_grid, mp_gather_spectral, mp_allgather_spectral
Point-to-point:    mp_exchange_latitude_halo
```

The immediate benefit is this: **there is only one copy of the model code**. The same physics or
dynamics code calls the same-named functions in serial and MPI builds; only the underlying
implementation differs.

### 3.3 The compile-time switch: `PLASIC_USE_MPI`

`plasic_mpi.c` performs the dispatch with a single preprocessor switch
(`src/mpi/plasic_mpi.c`):

```c
#ifndef PLASIC_USE_MPI
#define PLASIC_USE_MPI 0
#endif

#if PLASIC_USE_MPI
#include "mpi_native_backend.h"
#endif
```

Every `mp_*` function therefore has two implementation branches. For broadcast, for example
(`src/mpi/plasic_mpi.c`):

```c
int32_t mp_broadcast_integer(int32_t *buffer, int32_t count)
{
    if (buffer == NULL || count < 0)
    {
        return -1;
    }
#if PLASIC_USE_MPI
    return mpi_native_broadcast_integer(buffer, count);
#else
    return mpi_serial_broadcast_integer(buffer, count);
#endif
}
```

The compile-time switch is injected by `src/Makefile`:

```make
CPPFLAGS += -DPLASIC_USE_MPI=$(MPI)
```

So `PLASIC_USE_MPI` is not a runtime variable but a **compile-time constant**: the two
executables built from the same source follow two completely different backend code paths.

### 3.4 Division of labour between the two backends

The job of the **serial backend** is not to "pretend MPI exists". It degrades the multi-process
interface into the simplest possible single-process operations in a **semantically faithful**
way:

- Broadcast and reduction: with no peers, they simply return success (`mpi_serial_backend.c`);
- Gather: `copy_collective()` checks that `global_rows == local_rows` and then performs one `memcpy`;
- Halo exchange: with no neighbours, it returns success immediately and keeps the mirrored boundary values the caller has pre-filled.

The **native backend** is the real message-passing implementation: every collective operation
ends up in `MPI_Bcast`, `MPI_Allreduce`, `MPI_Allgather`, `MPI_Gather`, or `MPI_Sendrecv`.


### 3.5 Error-handling style

The PlaSiC `mp_*` interface does not use "kill the program immediately" approaches such as
`MPI_Abort()`. Instead it follows this pattern:
**check the arguments → return a status code (0 for success) → let the caller decide how to
handle it**. 

This style is consistent with the rest of the model, and it also lets MPI failures be converted
by upper layers into readable error messages in `runtime_set_error()`.

## 4. Domain Decomposition: What PlaSiC Parallelizes

**Domain decomposition** means cutting a large grid into pieces and giving them to several
processes. PlaSiC splits **along the latitude direction only**: each process owns all longitudes
and all vertical levels of the globe, but is responsible for one contiguous latitude band.

### 4.1 Latitude blocks

The correspondence between global latitudes and processes (PlaSiC convention:
**latitude indices increase from north to south**):

```text
Global Gaussian latitudes (north to south)
┌────────────────────────────────────────────┐
│ rank 0:              NLPP latitude circles │
│ rank 1:              NLPP latitude circles │
│ ...                                        │
│ rank NPRO-1:         NLPP latitude circles │
└────────────────────────────────────────────┘
Every rank also holds NLON longitudes and NLEV (or NLEP) vertical levels
```

### 4.2 Spectral coefficient blocks

Spectral space is also divided into **contiguous blocks**. The global number of spectral
coefficients per level is `PLASIC_NRSP`, and each process reserves `PLASIC_NSPP =
ceil(NRSP / NPRO)` slots of them (`src/state/plasicmod_state.h`). `NPRO` is no longer required to
divide `NRSP`: when it does not, the last rank owns only `NRSP - (NPRO-1) * NSPP` valid
coefficients and its trailing slots are padding. Padding is always zeroed, never communicated,
and never enters any physical computation; `plasic_nindex` is padded to `PLASIC_NESP = NSPP *
NPRO` so the last rank can index its whole block safely.

### 4.3 Global and local indices

The same physical quantity has two kinds of array, used for different purposes:

| Name | Size | Contents |
|---|---|---|
| `plasic_sd`, `plasic_sz`, `plasic_st`, `plasic_sq`, `plasic_sp` | `PLASIC_NRSP` | Every rank keeps the complete global spectrum |
| `plasic_sdp`, `plasic_szp`, `plasic_stp`, `plasic_sqp`, `plasic_spp` | `PLASIC_NSPP` | The local spectral block this rank is responsible for |

The grid-point state arrays, in contrast, are **local**: `plasic_gt`, `plasic_gq`, `plasic_gu`,
and so on are declared with `PLASIC_NHOR`, meaning that each process stores only its own latitude
band. When a global grid-point buffer is needed (spherical harmonic analysis, output, restart),
the function temporarily `malloc`s an array of size `PLASIC_NUGP`.

The position of a local block inside the global array is determined by the rank. PlaSiC provides
a unified offset query:

```c
int32_t mp_local_offset(int32_t local_rows)
{
    return active_rank * local_rows;
}
```

Spectral block offsets, however, are often written directly as `mp_rank() * PLASIC_NSPP`.

### 4.4 Latitude reordering at initialization

The Gaussian latitudes and Legendre weights are first computed in global order; then each
non-root process moves its own segment to the beginning of the array
(`src/runtime/runtime_initialization.c`):

```c
if (!mp_is_root())
{
    const size_t latitude_offset = (size_t)mp_rank() * (size_t)PLASIC_NLPP;

    memmove(plasic_sid, plasic_sid + latitude_offset,
            (size_t)PLASIC_NLPP * sizeof(plasic_sid[0]));
    /* likewise for gwd, csq, rcs */
}
```

Rank 0's offset is already 0, so it needs no move. After that, the code accesses only the first
`NLPP` elements of each array and no longer has to worry about global latitude indices. SHTns is
likewise told this process's latitude offset through `sht_init()`
(`src/runtime/runtime_initialization.c`):

```c
status = sht_init(
    PLASIC_NTRU, PLASIC_NLAT, PLASIC_NLON, PLASIC_NLPP,
    mp_rank() * PLASIC_NLPP);
```

### 4.5 Compile-time constraints

The decomposition sizes must be fixed at compile time, for a direct reason: every static array
declaration depends on `NLPP`, `NHOR`, and `NSPP`. MPI builds therefore add a mandatory
compile-time constraint (`src/state/plasicmod_state.h`):

```c
#if PLASIC_USE_MPI && (PLASIC_NLAT % PLASIC_NPRO) != 0
#error "MPI builds require PLASIC_NPRO to divide PLASIC_NLAT exactly"
#endif
```

The process count is checked again at runtime. `plasic_runtime_initialize()` passes the
compile-time constant `PLASIC_NPRO` to `mp_start()`; if the count given by `mpirun -np` does not
match, the model reports an error and exits immediately (`src/runtime/plasic_runtime.c`):

```c
mp_start_status = mp_start(PLASIC_NPRO, &process_count, &mpi_error);

if (mp_start_status != PLASIC_MP_START_OK)
{
    runtime_set_error(
        "parallel initialization failed: expected %d processes, "
        "got %d (backend status %d)",
        PLASIC_NPRO, process_count, mpi_error);
    /* ... */
    return PLASIC_RUNTIME_UNSUPPORTED_CONFIGURATION;
}
```

!!! important "NPRO is fixed at compile time"
    You cannot compile once and then run with a different `-np`. `PLASIC_NPRO` determines the
    size of the per-process arrays; when the process count does not match, the indices into the
    decomposed arrays become meaningless, so the model simply refuses to run.

## 5. Communication Primitives, One by One

This section pairs every function in `plasic_mpi.h` with its implementation in both backends.

### 5.1 Startup and shutdown: `mp_start` / `mp_stop`

**Semantics**: set up the parallel environment and answer "who am I, and how many of us are
there".

Native implementation (`src/mpi/mpi_native_backend.c`):

```c
status = MPI_Init(NULL, NULL);
active_world = MPI_COMM_WORLD;
if (status == MPI_SUCCESS)
    status = MPI_Comm_size(active_world, &size_value);
if (status == MPI_SUCCESS)
    status = MPI_Comm_rank(active_world, &rank_value);
```

It then compares `size_value` with `expected_processes`:

- Match → `PLASIC_MP_START_OK`;
- Mismatch → `PLASIC_MP_START_SIZE_MISMATCH` (`backend_started` is still set to 1, so that a later `mp_stop()` can call `MPI_Finalize()` normally);
- MPI itself fails → `PLASIC_MP_START_ERROR`.

The serial implementation (`src/mpi/mpi_serial_backend.c`) calls no MPI function at all: it just
sets `*processes = 1` and `*rank = 0`, and returns `PLASIC_MP_START_SIZE_MISMATCH` when
`expected_processes != 1`. This explains why a serial build must use `NPRO=1`.

On shutdown, the native backend synchronizes at a barrier before finishing
(`src/mpi/mpi_native_backend.c`):

```c
int status = MPI_Barrier(active_world);   /* wait until every process has arrived */
if (status == MPI_SUCCESS)
    status = MPI_Finalize();
active_world = MPI_COMM_NULL;
```

`MPI_Barrier` is a collective synchronization point: if any process has not arrived, all the
others wait there. It guarantees that `MPI_Finalize()` is not called prematurely while other
processes are still communicating.

### 5.2 Identity and layout: `mp_rank` / `mp_size` / `mp_is_root` / `mp_local_offset`

```c
int32_t mp_rank(void) { return active_rank; }
int32_t mp_size(void) { return active_processes; }
int32_t mp_is_root(void) { return active_rank == 0; }
int32_t mp_local_offset(int32_t local_rows) { return active_rank * local_rows; }
```

They answer the three most common questions in a parallel program: **who am I, how many of us
are there, and where does my piece of data start in the global array.**

### 5.3 Broadcast: `MPI_Bcast` and `mp_broadcast_*`

#### 5.3.1 The standard MPI function

**Purpose**: copy the data of the root process to every process in the communicator; a classic
one-to-many collective.

**Prototype**:

```c
int MPI_Bcast(void *buffer, int count, MPI_Datatype datatype,
              int root, MPI_Comm comm);
```

**Parameters**:

| Parameter | Direction | Meaning |
|---|---|---|
| `buffer` | root: input; others: output | Starting address of the data buffer |
| `count` | input | Element count (not bytes) |
| `datatype` | input | Element type, e.g. `MPI_FLOAT`, `MPI_INT` |
| `root` | input | Rank of the broadcasting source process |
| `comm` | input | Communicator |

Note that the same `buffer` argument is a **send** on the root and a **receive** on the other
processes; the call looks identical everywhere, and `root` determines the role.

**Semantics**:

```text
             ┌──────────┐
root process │  buffer  │
  rank 0     └──────────┘
                  │  MPI_Bcast
        ┌─────────┼─────────┐
        ▼         ▼         ▼
   rank 1     rank 2     rank 3
   buffer     buffer     buffer   ← contents match the root after the call
```

**Minimal example**:

```c
int value = (rank == 0) ? 42 : -1;
MPI_Bcast(&value, 1, MPI_INT, 0, MPI_COMM_WORLD);
/* after the call, value is 42 in every process */
```

#### 5.3.2 PlaSiC's wrapper and usage

The native backend wraps the `int32_t` and `float` versions separately
(`src/mpi/mpi_native_backend.c`):

```c
return (int32_t)MPI_Bcast(buffer, (int)count, MPI_INT32_T,
                          ROOT_RANK, active_world);
```

`ROOT_RANK` is fixed at 0, so PlaSiC callers never pass `root`. The serial implementation simply
returns 0: with one process, the data has effectively been "broadcast" already.

The typical use of broadcast in PlaSiC is **to let the root process read a file and share it with
everyone**. For example, the CO₂ forcing table (`src/runtime/co2_forcing.c`): the root process
scans and parses the CSV, and then

1. First broadcasts three integers of metadata (status code, start year, end year), so that every process knows what to do next;
2. Then broadcasts the whole concentration table (`mp_broadcast_real(forcing.table.values, ...)`).

The status code of restart writing is synchronized by broadcast as well, to avoid the situation
where **"the root process failed but the others still think it succeeded"**
(`broadcast_restart_status()` near `src/tools/restartmod_io.c`).

### 5.4 Global reduction: `MPI_Allreduce` and `mp_allreduce_real`

#### 5.4.1 The standard MPI function

**Purpose**: each process supplies one local piece of data, and MPI combines them into a single
result with a specified operation (sum, maximum, minimum, …) and **sends the result back to
every process**. This is MPI's **reduction** operation, in its "all" version (everyone gets a
copy).

**Prototype**:

```c
int MPI_Allreduce(const void *sendbuf, void *recvbuf, int count,
                  MPI_Datatype datatype, MPI_Op op, MPI_Comm comm);
```

**Parameters**:

| Parameter | Direction | Meaning |
|---|---|---|
| `sendbuf` | input | This process's local contribution |
| `recvbuf` | output | The reduced result, received by every process |
| `count` | input | Element count |
| `datatype` | input | Element type |
| `op` | input | Reduction operation, e.g. `MPI_SUM`, `MPI_MAX`, `MPI_MIN`, `MPI_PROD` |
| `comm` | input | Communicator |

**Semantics** (using `MPI_SUM` and `count = 1` as an example):

```text
rank 0: sendbuf = a0 ─┐
rank 1: sendbuf = a1 ─┤
rank 2: sendbuf = a2 ─┼──▶  a0 + a1 + a2 + a3  ──┬──▶ recvbuf (rank 0)
rank 3: sendbuf = a3 ─┘                          ├──▶ recvbuf (rank 1)
                                                 ├──▶ recvbuf (rank 2)
                                                 └──▶ recvbuf (rank 3)
```

**Minimal example**:

```c
float local = 1.0f * (float)(rank + 1);   /* ranks 0..3 contribute 1, 2, 3, 4 */
float total = 0.0f;
MPI_Allreduce(&local, &total, 1, MPI_FLOAT, MPI_SUM, MPI_COMM_WORLD);
/* total is 10.0 in all four processes */
```

**Three things to watch out for**:

1. `sendbuf` and `recvbuf` must not be the same memory (unless you use `MPI_IN_PLACE`); this is exactly why PlaSiC allocates a temporary array;
2. `op`, `count`, `datatype`, and `comm` must be identical on all processes;
3. Integer reductions are deterministic; floating-point reductions depend on the summation order and are **not guaranteed to be bitwise reproducible across different process counts**, so results should be compared with a tolerance.

A commonly confused point is the difference between `MPI_Reduce` and `MPI_Allreduce`:
`MPI_Reduce` gives the result only to the process named by `root`, while `MPI_Allreduce` gives
the result to every process.

#### 5.4.2 PlaSiC's wrapper and usage

Native implementation (`src/mpi/mpi_native_backend.c`):

```c
temporary = (float *)malloc((size_t)(count == 0 ? 1 : count) * sizeof(*temporary));
status = MPI_Allreduce(buffer, temporary, (int)count, MPI_FLOAT,
                       MPI_SUM, active_world);
if (status == MPI_SUCCESS && count != 0)
{
    memcpy(buffer, temporary, (size_t)count * sizeof(*buffer));
}
free(temporary);
```

This code is exactly an instance of the first caution above: it allocates a separate temporary
buffer as `recvbuf`, and after a successful reduction copies the result back into `buffer`.

PlaSiC uses only `MPI_SUM`, so `mp_allreduce_real()` does not expose an `op` parameter.

Its two typical uses in PlaSiC both concern **global consistency**:

1. **Enforcing global conservation**. The moisture fixer runs at the end of the physical
   processes: time stepping can produce small negative specific humidities, and the fixer's job
   is to remove those negatives while keeping the global total water amount unchanged. The
   procedure has four steps:

    1. `misc_prepare_fixer()` counts, grid point by grid point, the water "needed" by this process
       at each point (`moisture_needed`, stored in `work->horizontal_a`) and the water
       "available" for redistribution (`moisture_available`, stored in `work->horizontal_b`),
       and makes a copy of the specific humidity to be corrected (stored in `work->level_a`);
    2. `misc_fix_columns()` / `misc_fix_latitudes()` correct first within this process: anything
       that can be fixed inside a single column or a single latitude circle is fixed in place;
    3. `misc_local_totals()` sums the two remaining deficits of this process separately;
    4. `mp_allreduce_real()` adds the local sums of all processes into global totals, and finally
       `misc_finish_fixer()` completes the job using those global totals.

    The code and comments (`src/physics/physics_processes.c`):

    ```c
    /* Sum the two remaining deficits over the NLON×NLPP grid points of this process:
     *   totals[0] = water still missing in this process (sum of moisture_needed)
     *   totals[1] = water available in this process (sum of moisture_available) */
    misc_local_totals(
        PLASIC_NHOR, work->horizontal_a, work->horizontal_b, totals);

    /* Reduce two elements in one call, each summed independently:
     *   totals[0] = water still missing globally
     *   totals[1] = water available globally
     * After the reduction every rank holds exactly the same two numbers, which
     * is the precondition for all ranks to compute the same correction factor.
     * count=2 means each process contributes 2 elements. */
    if (mp_allreduce_real(totals, 2) != 0)
        return PLASIC_RUNTIME_NUMERICAL_FAILURE;

    /* Finish with the global totals:
     *   If a deficit remains (totals[0] > 0), all ranks use the same factor
     *       factor = (totals[1] - totals[0]) / totals[1]
     *   to scale the specific humidity being corrected (work->level_a) and clear
     *   the negative values; the correction is then converted into a humidity
     *   tendency through surface_pressure / (2Δt) / reference pressure,
     *   accumulated into plasic_gqdt, and the corrected values are written
     *   back to plasic_dq. */
    misc_finish_fixer(
        PLASIC_NHOR, PLASIC_NLEV, totals[0], totals[1], plasic_dp,
        plasic_delt2, plasic_psurf, work->level_a,
        plasic_dq, plasic_gqdt);
    ```

    The reason `count` is 2 is clear here as well: `totals` has exactly two elements, and MPI
    reduces them **element by element** rather than mixing the two quantities together. If only
    the first entry were reduced, the global available water would be meaningless, and the
    correct correction factor could not be computed.

2. **Collective error checking**. Turning "allocation failed" into a global vote
   (`src/runtime/co2_forcing.c`):

    ```c
    allocation_failure = forcing.table.values == NULL ? 1.0f : 0.0f;
    if (mp_allreduce_real(&allocation_failure, 1) != 0 ||
        allocation_failure != 0.0f)
    {
        /* If even one process failed, all processes take the same branch
           and exit with an error together */
    }
    ```

    This is a classic MPI idiom: error handling must also be collective. Otherwise, after the
    failing process exits, the other processes will hang in the later collective operations.

### 5.5 Allgather: `MPI_Allgather` and `mp_allgather_grid`

#### 5.5.1 The standard MPI function

**Purpose**: each process contributes one piece of data; MPI **concatenates the data of all
processes in rank order** and sends the complete result to every process.

**Prototype**:

```c
int MPI_Allgather(const void *sendbuf, int sendcount, MPI_Datatype sendtype,
                  void *recvbuf, int recvcount, MPI_Datatype recvtype,
                  MPI_Comm comm);
```

**Parameters**:

| Parameter | Direction | Meaning |
|---|---|---|
| `sendbuf` | input | The data contributed by this process |
| `sendcount` | input | Number of elements contributed by this process |
| `sendtype` | input | Send element type |
| `recvbuf` | output | Receive buffer, capacity at least `recvcount × size` |
| `recvcount` | input | Number of elements received from **each** process (not the total) |
| `recvtype` | input | Receive element type |
| `comm` | input | Communicator |

**Semantics**:

```text
rank 0: sendbuf = A ─┐
rank 1: sendbuf = B ─┤ concatenated in rank order
rank 2: sendbuf = C ─┤
rank 3: sendbuf = D ─┘
                   ┌───────────────────────┐
   every process's │  A  │  B  │  C  │  D  │
   recvbuf         └───────────────────────┘
```

**Minimal example**:

```c
float mine = 10.0f * (float)rank;
float all[4];   /* size = recvcount × size = 1 × 4 */
MPI_Allgather(&mine, 1, MPI_FLOAT,
              all, 1, MPI_FLOAT, MPI_COMM_WORLD);
/* every process's all is {0.0, 10.0, 20.0, 30.0} */
```

**Three things to watch out for**:

1. The most common mistake is to treat `recvcount` as the "total number of elements". It is the
   number of elements **from each process**, and the total receive-buffer capacity must be
   `recvcount × size`;
2. The concatenation order is strictly rank 0, rank 1, …, which is exactly why PlaSiC relies on
   "equal block sizes laid out contiguously in rank order";
3. The similar `MPI_Gather` gives the complete result only to `root`; `MPI_Allgather` gives the
   complete result to every process.

If processes contribute different numbers of elements, use `MPI_Allgatherv` (the variable-length
version with a `v`). PlaSiC gives every process an equal-sized block, so `MPI_Allgather` is
sufficient.

#### 5.5.2 PlaSiC's wrapper and usage

**Semantics**: each process hands over its own latitude band (`local_rows` horizontal points);
MPI assembles them into the complete global grid (`global_rows` points) and **sends the result
to every process**.

The fifth parameter is called `levels` in both `plasic_mpi.h` and the native backend; it
is the **number of vertical levels**. Data is stored **level-contiguously**:

```text
local:   [ layer 0: local_rows points ][ layer 1: local_rows points ]...
global:  [ layer 0: global_rows points ][ layer 1: global_rows points ]...
```

The native implementation performs one `MPI_Allgather` per level
(`gather_columns()` in `src/mpi/mpi_native_backend.c`):

```c
for (level = 0; level < levels && status == MPI_SUCCESS; ++level)
{
    if (gather_to_all)
    {
        status = MPI_Allgather(
            local  + (size_t)level * (size_t)local_rows,
            (int)local_rows, MPI_FLOAT,
            global + (size_t)level * (size_t)global_rows,
            (int)local_rows, MPI_FLOAT, active_world);
    }
    /* ... */
}
```

Note that the receive count is `local_rows`: each process contributes `local_rows` elements, and
MPI places them in rank order starting at `global + level * global_rows`. **This works only
because every process has an equal-sized block laid out contiguously in rank order**, which is
exactly PlaSiC's decomposition convention.

The serial implementation (`src/mpi/mpi_serial_backend.c`) degrades to a single semantically
equivalent copy:

```c
static int32_t copy_collective(
    float *global, const float *local, int32_t global_rows,
    int32_t local_rows, int32_t levels)
{
    if (global_rows != local_rows)
    {
        return -1;                       /* with one process the two must be equal */
    }
    memcpy(global, local,
           (size_t)local_rows * (size_t)levels * sizeof(*global));
    return 0;
}
```

Where PlaSiC puts it to work:

- **Spherical harmonic analysis**: SHTns needs the complete grid, so `gather_grid()` first assembles the global field and then transforms it (`src/math_tools/sht_kernels.c`);
- **Output**: frame output and monthly-mean output assemble the local accumulations into a global field and let the root process write NetCDF (`src/runtime/runtime_output.c`, `src/runtime/monthly_netcdf.c`);
- **Restart writing**: assemble the globe first, then let the root process write to disk (`src/tools/restartmod_io.c`);

### 5.6 Spectral gather: `mp_gather_spectral` and `mp_allgather_spectral`

Both share the same native-backend helper, `gather_spectral_columns()`; the only difference is
the final parameter, `gather_to_all`. Because the last rank's block may contain padding when
`NPRO` does not divide `NRSP`, this helper uses the variable-count versions
`MPI_Allgatherv` / `MPI_Gatherv` with

```text
counts[r]        = min(local_rows, max(global_rows - r * local_rows, 0))
displacements[r] = r * local_rows
```

`MPI_Gatherv` is exactly `MPI_Allgatherv`'s "root-only" version: its prototype has an extra
`root` parameter, and only the root process's `recvbuf` is written:

```c
int MPI_Gatherv(const void *sendbuf, int sendcount, MPI_Datatype sendtype,
                void *recvbuf, const int recvcounts[], const int displs[],
                MPI_Datatype recvtype, int root, MPI_Comm comm);
```

| Interface | Native call | Result |
|---|---|---|
| `mp_gather_spectral` | `MPI_Gatherv` (to the root) | **Only the root process** gets the full spectrum |
| `mp_allgather_spectral` | `MPI_Allgatherv` | **Every process** gets the full spectrum |

The receive side still starts each level at `global + level * global_rows` and fills exactly
`global_rows` valid elements in rank order, so the global spectral layout is unchanged. When
every rank has the same count (all `local_rows`, i.e. `NPRO` divides `NRSP`), the `*v` call is
bit-for-bit equivalent to the equal-count `MPI_Gather` / `MPI_Allgather` it replaces.

Under the serial backend, both reduce to `memcpy`.

How they are used:

- `mp_gather_spectral`: when writing restart files only the root process needs the full spectrum, and `MPI_Gather` expresses exactly this "root-only" semantics (in the current implementation, every rank still allocates an equally sized receive buffer to satisfy the uniform interface, but only the root's data is used) (`src/tools/restartmod_io.c`);
- `mp_allgather_spectral`: at the end of a dynamical time step, PlaSiC reassembles the scattered local spectral blocks into the complete spectrum so that every process can perform the subsequent global spherical harmonic synthesis. `gather_current_spectral_state()` does this five times in a row — for divergence, vorticity, temperature, humidity, and surface pressure (`src/runtime/runtime_dynamics.c`).

```text
mp_allgather_spectral(plasic_sd,  plasic_sdp,  NRSP, NSPP, NLEV);
mp_allgather_spectral(plasic_sz,  plasic_szp,  NRSP, NSPP, NLEV);
mp_allgather_spectral(plasic_st,  plasic_stp,  NRSP, NSPP, NLEV);
mp_allgather_spectral(plasic_sp,  plasic_spp,  NRSP, NSPP, 1);
mp_allgather_spectral(plasic_sq,  plasic_sqp,  NRSP, NSPP, NLEV);
```

### 5.7 Latitude halo exchange: `mp_exchange_latitude_halo`

This is the only function in `src/mpi/` that uses point-to-point communication, and it serves
the three-dimensional ocean. When the 3-D ocean computes meridional (north–south) differences,
it needs data from adjacent latitude rows. Each process holds only its own band, so it must ask
its neighbours for one extra row just outside the boundary. Such a row is usually called the
**halo** or **ghost cells**.


```text
row index      contents
  0            northern halo (from rank-1, or a mirrored boundary value)
  1..NLPP      the interior latitude circles of this process
  NLPP+1        southern halo (from rank+1, or a mirrored boundary value)
```

The neighbour relations (`src/mpi/mpi_native_backend.c`):

```c
north_neighbor = rank_value > 0 ? rank_value - 1 : MPI_PROC_NULL;
south_neighbor = rank_value < size_value - 1 ? rank_value + 1 : MPI_PROC_NULL;
```

Boundary processes have no neighbour; `MPI_PROC_NULL`
means "send to nowhere, receive from nowhere": the send becomes a no-op and the receive returns
immediately **without modifying the receive buffer**, so the mirrored values pre-filled by the
caller are preserved.

The exchange logic is carried out with two `MPI_Sendrecv` calls
(`src/mpi/mpi_native_backend.c`):

```c
/* First exchange (tag = HALO_NORTH_TAG): send north, receive from south */
MPI_Sendrecv(send_north, elements, MPI_FLOAT, north_neighbor, HALO_NORTH_TAG,
             recv_south, elements, MPI_FLOAT, south_neighbor, HALO_NORTH_TAG,
             active_world, &status);

/* Second exchange (tag = HALO_SOUTH_TAG): send south, receive from north,
   mirroring the first exchange */
MPI_Sendrecv(send_south, elements, MPI_FLOAT, south_neighbor, HALO_SOUTH_TAG,
             recv_north, elements, MPI_FLOAT, north_neighbor, HALO_SOUTH_TAG,
             active_world, &status);
```

Every process simultaneously "sends north and receives from the south"; the directions are
naturally complementary, and together with the atomicity of `MPI_Sendrecv` this avoids the
mutual-wait deadlock of Section 2.4. The two exchanges use different tags so that messages from
the first and second stages cannot be confused; MPI identifies a message uniquely by
"communicator + source + tag".

The caller must cooperate carefully as well. Take the 3-D ocean temperature field as an example
(`ocean3d_exchange_halo()` in `src/physics/physics_processes.c`):

1. Pack the northernmost and southernmost interior latitude rows of the extended field into `send_north` and `send_south`;
2. Copy the send buffers into the receive buffers as the initial mirrored values for boundary processes;
3. Call `mp_exchange_latitude_halo()`;
4. Write the received halo rows back into row 0 and row `NLPP+1` of the extended field.

Near the poles, where there is no neighbour, this initial value acts as a **zero-gradient boundary**; the latitude-coordinate halo is then overwritten by linear extrapolation.

The serial backend performs no communication at all and simply keeps the mirrored values
pre-filled by the caller (`src/mpi/mpi_serial_backend.c`), so the boundary handling has the same
semantics in serial and MPI builds.

## 6. The Complete MPI Data Flow in One Run

Putting all the pieces above back together gives one run of `plasic.x`. The stages below can be
used as a map when reading the code in `src/runtime/`.

### 6.1 Initialization

```text
plasic_runtime_initialize()
  ├─ mp_start(PLASIC_NPRO, ...)          → determine rank / size
  ├─ plasic_mypid = mp_rank()
  ├─ runtime_initialize_dynamics()
  │    ├─ gauss_inigau() + memmove()     → move this rank's latitude segment to the front of the arrays
  │    ├─ split_global_spectral()        → cut this rank's NSPP block out of the global spectrum
  │    └─ sht_init(..., mp_rank() * PLASIC_NLPP)
  ├─ read restart / orography / surface data
  │    └─ use mp_local_offset(PLASIC_NHOR) to read only this process's segment
  └─ physics_initialize()
       ├─ sea-ice climatology: mp_allgather_grid assembles the globe, diagnoses, then slices back to local
       └─ CO₂ forcing: root process reads the CSV → mp_broadcast_* distributes it
```

### 6.2 Dynamical core

PlaSiC's MPI dynamical core is **teaching-first** by design: every process keeps the complete
global spectrum and each one performs a full SHTns spherical harmonic transform, except that
during synthesis only this process's latitude band is written into the local grid-point arrays.
The flow is:

```text
runtime_spectral_adiabatic()
  ├─ each process updates only its own NSPP spectral block (spectrala_implicit / spectrala_finalize)
  └─ gather_current_spectral_state()
       └─ mp_allgather_spectral ×5        → reassemble the complete spectrum

synthesize / analyse (SHTns adaptation layer)
  ├─ synthesis: every process runs the full SHT, copying only this rank's latitude rows
  └─ analysis: mp_allgather_grid assembles the full grid-point field → every process runs the full SHT
```

The advantage of this scheme is that the parallel and serial code paths are almost identical,
which is convenient for teaching, debugging, and low-to-medium-resolution experiments. The price
is that memory and computation do not shrink ideally with the number of processes (every process
keeps global temporary fields). 

### 6.3 Physical parameterizations

Physical parameterizations are computed only on the **local grid band** and need almost no
communication; the two exceptions are:

- **Globally conserved quantities**: use `mp_allreduce_real` when a global total is needed (such as the moisture fix in Section 5.4);
- **North–south differences in the 3-D ocean**: use `mp_exchange_latitude_halo` when adjacent latitudes are needed (Section 5.7).

### 6.4 Output and restart

All file I/O follows the same pattern: **first assemble the global field with collective
communication, then let only the root process touch the file, and finally broadcast the write
status**.

```text
Frame output / monthly means:
  local accumulation ──mp_allgather_grid──▶ global field ──root writes NetCDF──▶ mp_broadcast_* syncs status

Restart writing:
  local grid points ──mp_allgather_grid──▶ global grid points ──┐
  local spectrum    ──mp_gather_spectral─▶ global spectrum    ──┴─▶ root writes to disk
```

This avoids overwrites or races caused by several processes writing the same file at once, and
it also lets all processes learn about a write error on the root side through the broadcast.

### 6.5 Finalization

```text
plasic_runtime_finalize()
  └─ mp_stop()   → MPI_Barrier + MPI_Finalize, or a serial return of 0
```

## 7. Building and Running

### 7.1 Environment setup

The MPI build needs Open MPI (on macOS):

```bash
brew install open-mpi
```

The MPI-related defaults in `src/Makefile` are at the top of the file (`MPI ?= 1`, `NPRO ?= 2`,
`MPI_CC ?= mpicc`, `MPIRUN ?= mpirun`) and can be overridden on the command line. To avoid
confusion from implicit defaults, always write the configuration explicitly.

Build the serial reference version:

```bash
make -C src MPI=0 NPRO=1
```

Build the two-process MPI version:

```bash
make -C src MPI=1 NPRO=2
```

The build directory name automatically carries a configuration suffix, for example
`build/T31_L13_MPI_P2_O16/plasic.x`. The compile-time switch is passed as
`-DPLASIC_USE_MPI=1`; when `MPI=1`, the compiler is switched to `$(MPI_CC)` (default `mpicc`),
and the native backend source file is added to the compilation list (`src/Makefile:296`).

### 7.2 Running

The Makefile's `run` target automatically prefixes the program with `$(RUNNER)` (that is,
`mpirun -np NPRO`):

```bash
make -C src run STEPS=64
```

You can also launch it manually:

```bash
mpirun -np 2 build/T31_L13_MPI_P2_O16/plasic.x \
  --data-dir src/data/surface \
  --co2-ppm 280 \
  --steps 64 \
  --output run/T31_L13_MPI_P2_O16/status
```

The number after `mpirun -np` must match the compile-time `NPRO` exactly; otherwise the run
stops with the "expected … processes, got …" error shown in Section 4.5.
