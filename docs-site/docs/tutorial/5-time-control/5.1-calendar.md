# 5.1 Calendar

PlaSiC represents time at two levels:

- **Step count `plasic_nstep`**: the only clock that advances. It increases by one after each
  dynamical step.
- **Calendar date `plasic_ndatim[7]`**: a derived value converted from the step count. It is used
  for the seasonal radiation cycle, CO₂ lookup, climatological-field interpolation, and output.

The conversion depends entirely on the **calendar type**. Both calendars use the same epoch:

```text
nstep = 0  ≡  Year 0, January 1, 00:00
```

The calendar type therefore defines the mapping between `nstep` and the date. **Changing the
calendar changes the date represented by the same `nstep`.** The calendar type is stored in the
restart file and is used to interpret `nstep` during a warm start.

All calendar arithmetic is implemented in `src/tools/calmod_kernels.c`. Physics, output, and
monthly-mean NetCDF routines use the same interfaces instead of maintaining separate calendar
rules.

---

## 1. Calendar types

| Name | Value | Meaning |
|---|---:|---|
| `PLASIC_CALENDAR_GREGORIAN` | 0 | Proleptic Gregorian calendar: 365 days in a common year and 366 days in a leap year, with standard Gregorian month lengths. Year 0 is divisible by 400 and is therefore a leap year. |
| `PLASIC_CALENDAR_FIXED_360` | 1 | 12 months × 30 days = 360 days, with no leap years. |

Select the calendar as follows:

| Calendar | CLI | JSON |
|---|---|---|
| Gregorian (default) | `--calendar gregorian` | `"calendar": "gregorian"` |
| 360-day | `--calendar 360day` | `"calendar": "360day"` |

- For a **cold start** (without `--restart`), this option selects the calendar.
- For a **warm start**, the `calendar` record in the restart file takes precedence. If the
  CLI or JSON setting conflicts with the file, PlaSiC ignores the setting and prints a message.
  If the file has no `calendar` record, PlaSiC uses **Gregorian (0)** because restart files from
  earlier versions used Gregorian calendar semantics.

## 2. Time step: fixed by resolution

`runtime_initialize_dynamics()` in `src/runtime/runtime_initialization.c` derives the time-step
parameters (`plasic_mpstep`, `plasic_ntspd`, `plasic_deltsec`, and `plasic_delt`) from the
**latitudinal resolution**. These parameters cannot be changed through the CLI or JSON. To
change them, select another resolution and rebuild PlaSiC.

| Quantity | Meaning | Value or calculation |
|---|---|---|
| `plasic_mpstep` | Minutes per dynamical step | `NLAT ≤ 32`: 45; `NLAT ≤ 48`: 36; otherwise $(30\times64)/\mathrm{NLAT}$ |
| `plasic_ntspd` | Steps per solar day | `round(solar_day)/(mpstep×60)`, then forced to an even number |
| `plasic_solar_day` / `plasic_sidereal_day` | Length of the solar/sidereal day in seconds | 86400 / 86164.0916 (defined in `src/tools/p_earth_kernels.c`) |
| `plasic_deltsec` / `plasic_delt` | Dimensional/dimensionless time step | `solar_day/ntspd`; $2\pi/\mathrm{ntspd}$ |

Other retained time-related quantities are:

- `plasic_nafter = ntspd`: the output accumulation window, reset once per model day.
- `plasic_naccuout`: the number of samples in the current window, stored in restart files.
- `plasic_nkits`: the number of explicit Euler steps during startup. It is set to 0 at runtime,
  so both cold and warm starts enter the leapfrog scheme directly. It also gates atmosphere-ocean
  and sea-ice coupling. Because it is always 0 at runtime, this gate remains open.

`--steps N` specifies the number of **dynamical steps**. A missing or zero value produces an
error.

## 3. Cold starts: specify the initial date on the command line

```bash
plasic.x --steps 960 \
  --calendar gregorian \
  --start-year 1850 --start-yday 1 --start-hour 0 --start-minute 0 \
  --co2-ppm 284.3 --data-dir data/surface \
  --output run/status
```

PlaSiC checks the following constraint before integration begins:

- **The specified hour and minute must lie on a step boundary.** Each day is divided evenly
  into `ntspd` steps, so the specified time must be the exact start of a step. For example, at
  T21 (45 minutes per step, `ntspd = 32`), `00:45` and `01:30` are valid, but `00:10` and
  `00:30` are not.

## 4. Warm starts: the restart file takes precedence

```bash
# Continue directly from the saved state
plasic.x --restart run/status --steps 11680 --co2-ppm 284.3 --output run/status_next

# Set nstep in the restart state directly to 1850-01-01 (T21, Gregorian)
plasic.x --restart spinup.restart --steps 1928480 \
  --reset-nstep 21622368 --co2-forcing CO2.csv --output historical/status
```

`--reset-nstep` changes only the clock and date label. It **does not change the physical
state**. Use it to move a spin-up snapshot to a target epoch, such as 1850. PlaSiC prints a message like this:

```text
--reset-nstep: nstep 4 -> 11712, model date 1-01-01 00:00 (gregorian calendar)
```

Time conversion follows this order: read `nstep` and `calendar` from the restart file, apply
the optional `--reset-nstep`, call `step2cal()` to populate `plasic_ndatim`, and initialize the
physics using the resulting month and season.

### Historical experiment workflow
**Start the historical experiment from a balanced restart file.** For a T21 Gregorian run, set
   the clock back to 1850 with `--reset-nstep 21622368`. Then use `--steps 1928480` to cover
   1850–2014. The physical state remains unchanged; only its date label is replaced.

Use the following formulas to calculate `--steps` and `--reset-nstep` for either calendar:

$$
N = \bigl(D_1 - D_0\bigr)\times \mathrm{ntspd},
\qquad
S_{\mathrm{reset}} = D_0 \times \mathrm{ntspd},
$$

where $D_0$ is the number of days from the epoch (Year 0, January 1) to the start date. $D_1$
is the number of days from the epoch to the day after the end date, that is, the end of the
requested integration interval. Both values must be calculated using the selected calendar.

**Example: how are `--reset-nstep 21622368` and `--steps 1928480` obtained for a T21/L10
historical experiment covering 1850–2014?**

First, determine `ntspd`. For T21, `NLAT = 32`, so `mpstep = 45` minutes per step and
`ntspd = 1440 / 45 = 32` steps per day.

Second, calculate the cumulative number of Gregorian days. The number of days $D(y)$ from
Year 0, January 1, to January 1 of year `y` is given by the following proleptic Gregorian
formula, where integer division rounds down:

$$
D(y) = 365y + \left\lfloor\frac{y+3}{4}\right\rfloor
                - \left\lfloor\frac{y+99}{100}\right\rfloor
                + \left\lfloor\frac{y+399}{400}\right\rfloor
$$

Substitute the start and end years:

| Quantity | Calculation | Result |
|---|---|---:|
| $D(1850)$ | $365\times1850 + 463 - 19 + 5$ | 675 699 days |
| $D(2015)$ | $365\times2015 + 504 - 21 + 6$ | 735 964 days |
| $D(2015)-D(1850)$ | 735 964 − 675 699 | 60 265 days |

Third, multiply by `ntspd`:

```text
--reset-nstep = D(1850) × 32              = 675699 × 32 = 21622368
--steps       = (D(2015) - D(1850)) × 32  =  60265 × 32 =  1928480
```

The calculation for the **360-day calendar** is the same except that $D(y) = 360y$. At
`ntspd = 32`, the step count for 1850-01-01 is
$1850 \times 360 \times 32 = 21312000$. A 165-year run requires
$165 \times 360 \times 32 = 1900800$ steps.

Use the following commands to calculate values for other Gregorian dates:

```bash
# Initial step: D(y) * ntspd
python3 -c "y=1850; print((365*y+(y+3)//4-(y+99)//100+(y+399)//400)*32)"
# Total steps: (D(end+1) - D(start)) * ntspd
python3 -c "d=lambda y:365*y+(y+3)//4-(y+99)//100+(y+399)//400; print((d(2015)-d(1850))*32)"
```

## 5. Calendar interfaces

`src/tools/calmod_kernels.c` implements all calendar arithmetic. The interfaces are declared
in `calmod_kernels.h`:

| Interface | Direction or purpose | Description |
|---|---|---|
| `cal2step(calendar, year, yday, hour, minute, &step)` | Date → step count | Converts a cold-start date |
| `step2cal(calendar, step, datim)` | Step count → date | Supports both calendars; `datim = [year, month, day, hour, minute, weekday, leap-year flag]` |
| `ndayofyear(calendar, step)` | Step count → day of year | Returns 1–365/366 for Gregorian or 1–360 for the 360-day calendar; used by the seasonal radiation cycle |
| `days_in_month(calendar, year, month)` | Month length | Used by monthly-mean output and `momint` interpolation |
| `days_in_year(calendar, year)` | Year length | Returns 365/366 for Gregorian or 360 for the 360-day calendar; used as the radiation-year length |
| `days_before_year(calendar, year)` | Cumulative day count | Returns the number of days from the epoch (Year 0, January 1) to January 1 of `year`, equal to the total length of years 0 through `year - 1` |
| `days_before_month(calendar, year, month)` | Cumulative day count | Returns the number of days from the epoch (Year 0, January 1) to the first day of `month` in `year` |
| `momint(calendar, step, &month_a, &month_b, &weight)` | Monthly climatology interpolation | Uses calendar-specific month lengths and midpoints; returns the two adjacent months and an interpolation weight. An adjacent month may be 0 or 13, as defined by the 14-slot climatology. |

## 6. Time records in restart files

| Record | Type | Status | Description |
|---|---|---|---|
| `nstep` | int32 | Retained, **required** | PlaSiC reports an error and cannot continue the integration if this record is missing. |
| `calendar` | int32 | **New** (0/1) | Used to interpret `nstep` during a warm start; always written to new restart files. If absent from an older file, PlaSiC uses 0. |
| `naccuout` | int32 | Retained | Output accumulation counter; independent of model time. |
| `seed` | int32[8] | Retained | Random-number state; independent of model time. |

`plasic_ndatim`, `plasic_nafter`, `plasic_ntspd`, `plasic_mpstep`, `plasic_deltsec`, and
`plasic_nkits` are not stored in restart files. They are derived either from `nstep` and
`calendar` or from the model resolution. See
[6.4 Inside a Restart File](../6-experiments/6.4-restart-file-format.md#31-metadata-and-seed) for details.
