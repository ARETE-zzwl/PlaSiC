# 6.4 Inside a Restart File: The Structure of `earth_t85_l25.restart` { #restart-file-format }

A restart file is the model's own memory dump. It stores every prognostic variable needed to
continue an integration from the exact point where a previous run stopped. This note dissects
`src/data/earth_t85_l25.restart`, the standard warm-start state of the T85/L25 configuration,
and answers three questions:

1. how is the file physically organised?
2. which variables does it contain?
3. how are those variables ordered inside each record?

The file shown here was written by `plasic_runtime_write_restart()`
(`src/runtime/plasic_runtime.c`); its atmosphere is read back by
`runtime_load_atmosphere_restart()` (`src/runtime/runtime_initialization.c`), its surface
components by `physics_initialize()` (`src/physics/physics_initialization.c`). The low-level
record I/O lives in `src/tools/restartmod_io.c`, and the physical meaning of every field is
tabulated in [1.3 Global State Variables](../1-user-guide/1.3-global-state-variables.md#plasic-state-variables).

## 1. The container: sequential unformatted records

The file is not a self-describing archive such as NetCDF or HDF5. It follows the classic
Fortran *sequential-unformatted* convention: every logical record is wrapped in two 4-byte
markers that repeat its payload length,

```text
[uint32 L] [L bytes of payload] [uint32 L]
```

and all values are written in the machine's **native byte order** (little-endian on ordinary
x86 and ARM machines). 

Each variable occupies **two consecutive records**: a *name record* whose payload is always the
fixed 16-byte, blank-padded variable name, followed by a *data record* that holds the values.
The fixed sizes are enforced by `_Static_assert` in `restartmod_io.c:44`, so the format cannot
silently change with the platform's `int` width.

Table 6.4.1 gives the byte map of one variable, and Figure 6.4.1 shows the first bytes of the
example file.

**Table 6.4.1 — Byte-level layout of one variable (one name record + one data record)**

| Offset from record start | Size | Content |
|---:|---:|---|
| 0 | 4 | `16` — length of the name record |
| 4 | 16 | variable name, ASCII, right-padded with blanks |
| 20 | 4 | `16` — trailing marker of the name record |
| 24 | 4 | `N` — payload length in bytes |
| 28 | N | payload (32-bit integers or 32-bit floats, see §4) |
| 28 + N | 4 | `N` — trailing marker of the data record |

Every variable therefore costs `N + 32` bytes on disk (24 bytes of name record and 8 bytes of
data-record markers). In the example file the first record is `nstep`:

```text
offset   bytes                                   interpretation
0x00     10 00 00 00                             uint32 16, opening marker of the name record
0x04     6e 73 74 65 70 20 20 20 20 20 20 20     "nstep" + 7 of its 11 trailing blanks
0x10     20 20 20 20 10 00 00 00                 the last 4 blanks + uint32 16, closing marker
0x18     04 00 00 00                             uint32 4, opening marker of the data record
0x1c     30 75 00 00                             int32 30000
0x20     04 00 00 00                             uint32 4, closing marker of the data record
```

*Figure 6.4.1. The `nstep` variable: name record (24 bytes) followed by a 4-byte data record.*


The multi-byte values are read in the same native byte order as everything else, so on a
little-endian machine the four bytes `10 00 00 00` form the 32-bit integer `0x00000010` = 16
(the least significant byte comes first), and `30 75 00 00` is `0x00007530` = 30000.

The name bytes are plain ASCII codes: `6e` = `n`, `73` = `s`, `74` = `t`, `65` = `e`,
`70` = `p`, and `20` = space.

## 2. A dictionary in effect, not by construction

Reading happens in two steps.

1. **Scan once, at open time.** `restart_open_read()` walks through the whole file from the first
   record to the last. For every variable it writes down three facts in a small in-memory table:
   the name, the byte offset where the data record's payload begins, and how many bytes that
   payload holds. Each table entry is one `restart_record` (`restartmod_io.c`).
2. **Look up and read, on every request.** Later, when the model asks for a variable,
   `restart_read_integer()`, `restart_read_array()`, and friends search this table for the name,
   jump the file position straight to the stored offset, and read only the bytes they need.

For example, the scan finds that `nstep` starts at offset `0x1c` and is 4 bytes long, so any
later request for `nstep` seeks to `0x1c` and reads those 4 bytes.

The file therefore behaves like a dictionary from name to payload — but **only because the
reader builds that dictionary in memory while opening the file**. Nothing dictionary-like is
stored on disk, and the table is discarded when the file is closed and rebuilt on the next open.

Table 6.4.2 lists the consequences worth remembering.

**Table 6.4.2 — Properties of the name-keyed lookup**

| Property | Consequence |
|---|---|
| Names are exactly 16 bytes, blank-padded, case-sensitive | names longer than 16 bytes are truncated at write time |
| Lookup returns the **first** match | a duplicate name silently shadows every later copy |
| No type tag and no shape field | the reader must know whether a record is integer or float, and how many values it holds; a 4-byte record could be either one `int32` or one `float` |
| No magic number, version, or directory | any sequence of well-formed records scans successfully; only the dimension checks on `nlat/nlon/nlev/nrsp` confirm that the content matches the executable |
| Payload size may exceed what the reader asks for | `restart_read_array()` accepts oversized records and reads the leading bytes only |
| Nothing about parallelism | every field is written as a full global array, so any number of MPI ranks can read the same file |
| Native byte order | files are not portable between little-endian and big-endian machines |
| A successful open requires fewer than 200 records | `RESTART_MAX_RECORDS = 200` is the array bound: the scanner rejects a file once 200 records have been indexed, so at most 199 variables can be read (the example holds 131) |

## 3. Inventory of `earth_t85_l25.restart`

The file describes a T85/L25 state: `NLAT = 128` Gaussian latitudes, `NLON = 256` longitudes,
`NLEV = 25` σ levels, `NTRU = 85`, `NRSP = 7482` real spectral coefficients per level, and a
global grid of `NUGP = NLON × NLAT = 32 768` points. The deep ocean carries 16 layers, and all
climatologies carry 14 months.

It contains **131 variables** and 52 178 776 bytes, which decomposes exactly as

```text
52 178 776 B  =  52 174 584 B of payload  +  131 × 32 B of record framing
```

Table 6.4.3 groups the records by module; §3.1–§3.8 list every name. Shapes are written as
`R × C` in the storage sense defined in §4: `R` values per column, `C` columns.

**Table 6.4.3 — Record groups in the example file**

| Group | Records | Payload (B) | Notes |
|---|---:|---:|---|
| Metadata and seed | 7 | 56 | clock, grid dimensions, RNG seed |
| Atmosphere, spectral | 12 | 6 823 584 | seven current + five previous-time-level fields |
| Atmosphere, grid | 36 | 14 155 776 | 33 two-dimensional + 3 level-resolved fields |
| Land surface | 13 | 7 208 964 | includes three 14-month climatologies |
| Mixed-layer sea | 14 | 1 703 940 | surface state and coupling accumulators |
| Sea ice | 33 | 9 043 980 | includes three 14-month climatologies |
| Slab ocean | 10 | 2 752 520 | single-layer mixed layer |
| Deep ocean (3-D) | 6 | 10 485 764 | five `NUGP × 16` fields |

### 3.2 Atmosphere: spectral state (12 records)

The dynamical core stores the state as spherical harmonic coefficients, in the triangular
ordering described in [2.3 Spherical Harmonic Spectra & Transforms](../2-dynamical-core/2.3-spectral-transform-and-fft.md#61-layout-of-spectral-coefficients)
(`m` outer, `n` inner, real and imaginary parts interleaved).

= \bigl(9\times 7482\times 25 + 3\times 7482\bigr)\times 4\ \mathrm{B}
= 6\,823\,584\ \mathrm{B},
$$

the value listed for this group in Table 6.4.3.

## 4. How each payload is ordered

All payloads share one convention: **the last array index runs fastest**, i.e. the values are
stored column by column. A record declared `R × C` is written as `C` consecutive blocks of `R`
values:

```text
[ column 0: rows 0 … R−1 ] [ column 1: rows 0 … R−1 ] … [ column C−1: rows 0 … R−1 ]
```

In C this is exactly the memory layout `array[row + column * R]` used throughout
`src/state/plasicmod_state.h`, which is why writing and reading an array is a straight
`fwrite`/`fread` of contiguous memory. The meaning of “row” and “column” depends on the field
type:

| Field type | Rows (`R`) | Columns (`C`) | Row order |
|---|---|---|---|
| Spectral field, e.g. `st` | `NRSP = 7482` modes | `NLEV = 25` levels | triangular mode order, each mode as consecutive real, imaginary parts |
| Two-dimensional grid field, e.g. `dls` | `NUGP = 32 768` points | 1 | Gaussian latitudes north → south, longitude running fastest within a row |
| Level-resolved grid field, e.g. `dcc` | `NUGP` points | `NLEV` levels | same point order, one column per level |
| Deep-ocean field, e.g. `deept` | `NUGP` points | 16 layers | same point order |
| Land climatology, e.g. `dtcl` | `NUGP` points | 14 months | same point order |
| Soil temperature `dsoilt` | `NUGP` points | 5 layers | same point order |
| Scalar, e.g. `nstep` | 1 | 1 | — |

For example, the 748 200-byte payload of `st` is 25 blocks of 7482 floats
(`7482 floats × 4 B/float × 25 levels = 748 200 B`); block `k` holds the
complete spectrum of temperature at level `k` (indices 0 and 1 are the real and imaginary parts
of mode `(m = 0, n = 0)`, and so on). The 3 276 800-byte payload of `dcc` is 25 blocks of
32 768 grid points, level by level.

Two properties of the parallel implementation are worth noting here:

- Grid and spectral fields are **global** in the file. At write time each rank contributes its
  latitude band or spectral block, and the helper routines (`restart_write_distributed_grid()`,
  `restart_write_distributed_spectral()` in `restartmod_io.c`) gather them into complete arrays
  before the root process writes. The payload therefore does not depend on `NPRO`, and a file
  written by 160 ranks reads back identically on one rank.
- Reading a single rank's slice does **not** read the whole record: `restart_read_array_slice()`
  seeks once per column and reads only the rows that belong to the calling rank. This is why the
  column-major layout matters in practice.

## 5. What the restart file does not contain

The file is deliberately minimal: everything that can be recomputed deterministically is
recomputed at startup instead of being stored.

- **Geometry and operators.** Gaussian latitudes, quadrature weights, σ levels, reference
  profiles, sponge time scales, and the matrices produced by `initpm_vertical()`,
  `initpm_spectral()`, and `makebm()` are rebuilt from the compile-time resolution and the
  fixed physical constants.
- **Derived atmospheric fields.** Surface pressure `dp`, grid-point winds and temperature,
  radiation fluxes, physics tendencies, and the `g*` work arrays are regenerated from the
  spectral state on the first time step. Only the surface entries of `dt` and `dq` are stored,
  because the physics needs them before the first transform.
- **The calendar date.** The file stores the step counter `nstep` and the calendar kind
  `calendar`, but no date. Both are needed because the calendar decides how `nstep` maps to a
  date: the same `nstep` means a different day under Gregorian and under the 12 × 30-day
  calendar. The model clock
  `plasic_ndatim = [year, month, day, hour, minute, weekday, leap flag]` is derived by
  `step2cal(plasic_calendar, plasic_nstep, ...)` at startup and after every step, using the
  steps-per-day `plasic_ntspd`.
  - **Cold start** (no `--restart`): `--calendar gregorian|360day` selects the calendar and
    `--start-year`, `--start-yday` (1-based day of year), `--start-hour`, `--start-minute`
    (defaults 0, 1, 0, 0) define the starting date. `cal2step()` converts it into
    `plasic_nstep`; the starting time must fall exactly on a time-step boundary.
  - **Warm start**: `nstep` and `calendar` are read from the file. A missing `nstep` is a fatal
    error; a missing `calendar` is read as Gregorian (0), which is what old files mean. The
    `--calendar` option is ignored with a warning when it disagrees with the file, and
    `--reset-nstep N` replaces the stored `nstep` with `N` after loading, re-basing the clock
    while the physical state stays as stored (the new model date is printed).
  - The epoch is fixed in both calendars: `nstep = 0 ≡ year 0, January 1, 00:00`. The calendar
    kinds, month lengths and year lengths are implemented once in `tools/calmod_kernels.c`;
    nothing about them is stored in the restart beyond the kind.
- **The MPI decomposition.** No rank count, block sizes, or halo rows are stored; the deep-ocean
  halo rows are rebuilt after load.
- **Diagnostics.** Monthly means and other output live in the separate NetCDF files; the
  restart keeps only the accumulators that are still open when the file is written.

One practical consequence: on a warm start `--data-dir` is irrelevant. The surface NetCDF files
are read only by the cold-start paths (`initialize_cold_start_atmosphere()` and
`load_surface_initialization()`; see
[6.5 Cold-Start Surface Boundary Fields at T42](6.5-cold-start-surface-fields-t42.md)
for the file-by-file map); a restart treats the records it loads as authoritative. Even
fields that older restart files lack are not taken from the NetCDF data: the deep-ocean records
of §3.8, for example, are re-seeded from the mixed-layer temperature by
`physics_ocean3d_initialize()`.
